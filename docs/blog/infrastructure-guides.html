Infrastructure documentation as part of the platform

How I approached Terraform and Terragrunt guides, workflow examples, and recovery instructions so another engineer could make a change without having to reverse-engineer the platform first.

At CLARK, I wrote Terraform and Terragrunt guides and best practices alongside our infrastructure workflow. They covered why we used each tool, how configuration was organized, how engineers worked through Atlantis, and how reusable module versions fit into the process.

I see this as engineering work, not an afterthought. A platform can be technically correct and still hard to use if the important decisions live in the heads of the people who built it. A teammate can know AWS and Terraform well and still know nothing about our state layout, inherited configuration, release conventions, or who's allowed to apply.

My aim was to tie each explanation to the next task. Someone should know where to make a change, what result to expect, what to review, and what to do when the workflow gets stuck. The best guide is the one an engineer can keep open while doing real work.

Start with the tasks engineers actually have

One long reference page rarely helps at every moment. A new engineer making a small change needs a short path through prerequisites and review. Someone upgrading a module needs compatibility and migration details. Someone investigating a failed apply needs current evidence and a recovery decision.

We already had pages on why we chose the tools, style guides, dependency guides, Atlantis configuration, and repository instructions. I'd organize all of that around a few entry points:

TaskGuide should answerEvidence the reader should leave with
Make a first infrastructure changeWhich repository, unit, tools, and permissions do I need?A reviewed plan tied to the intended environment
Add another environment or componentWhich shared configuration and module should I reuse?A clear state location, owner, and dependency relationship
Upgrade a moduleWhat changed and what migration is required?A plan with understood resource impact
Import an existing resourceWhich resource address and identity belong together?A subsequent plan confirming the configuration
Recover from a failed operationWhat ran, what changed, and who is still writing?A safe next step based on current state
Investigate an old DTEWho owns it and which lifecycle applies?A deliberate retain, remind, or remove decision

That keeps the overview short while the deeper material is there exactly when someone needs it.

Explain why the tools are there

Our "Why Terragrunt?" guide covered less duplication, shared backend configuration, explicit dependencies, consistent environments, and the configuration hierarchy. Our "Why Atlantis?" guide covered automation, plan review, coordination, auditability, and fewer repetitive manual steps.

Those reasons should lead straight into how things are built. Terragrunt handles the relationship between shared settings and a leaf deployment. Atlantis brings plan and apply into the pull request. Terraform still describes resources and works out their changes. A separate module repository provides reusable implementations with explicit release references.

Once an engineer has that picture, they can work out where a change belongs. If the application needs a different module input, edit the consumer. If the module needs new behavior, change and release the module. If a plan isn't being triggered, look at project mapping and workflow configuration instead of rewriting the Terraform resource.

I'd put a small architecture diagram and one leaf example near the top, then link out to the detailed references. Nobody should have to memorize the whole platform before making a normal change.

A worked guide for the ordinary change

Our documented workflow asked engineers to work on a branch, run local checks, open a pull request, review the Atlantis output, get approval, and apply through Atlantis. It discouraged local applies and relied on the automation to merge successful changes.

Below is a reconstructed guide built on that workflow. It shows what I'd include for the reader, without internal account details.

Prerequisites and scope

Before editing, identify the provider, account or project, region, environment, component, and owning team. Check that the directory you picked maps to the remote state you intend. Confirm you have repository access and the supported tool versions.

Install the local checks using the documented setup. The module repository and the live infrastructure repository run different checks, so the guide shouldn't promise validation that your checkout doesn't actually run.

bash
pre-commit install
pre-commit run --all-files

You should see the relevant formatting, repository hygiene, and configured validation checks pass. Passing local checks gets you ready for review; it doesn't prove the infrastructure will apply safely.

Make the smallest coherent change

Use an existing unit with the right scope, or follow a documented example for a new one. Keep unrelated version bumps and file reshuffles out of a small behavior change where you can. A reviewer should be able to say why each part of the diff is there.

For a module upgrade, note the old reference, the new reference, and the expected behavior in the pull request. For a new unit, explain its dependencies and state boundary. For a change to a shared parent, list which leaf units it affects.

Read the plan as a reviewer

Atlantis should produce plans for the projects you meant to change. The guide has to tell the reader what to look at, not just say "check the plan."

  • Identify every replacement and deletion, including why Terraform selected it.
  • Check account, project, region, and resource names against the intended scope.
  • Inspect permission changes and externally reachable resources.
  • Check dependent units and whether their outputs will change.
  • Confirm that module and provider versions match the expected implementation.
  • Regenerate the plan if code, relevant state, or upstream outputs have changed.

The goal of review is an operation everyone understands, not a green check next to a list of changes nobody explained.

Apply and verify

Once the configured approval and mergeability requirements were met, the documented command path was:

text
atlantis plan
atlantis apply

These are pull-request comments, not commands to run against infrastructure from a laptop. In a repository with many projects, the guide should show the project-selection syntax that matches its actual configuration and installed Atlantis version.

After the apply, check the execution result and how the service behaves. Terraform success is one signal; application readiness, connectivity, and monitoring are others. If automatic merge is configured, confirm the workflow finished instead of merging by hand just to make the pull request go away.

Teach Terraform and Terragrunt dependencies separately

Our guides covered both kinds of dependency, and this is exactly where loose wording leads to wrong expectations in operations.

Inside one Terraform configuration, references between resources build the resource graph. An explicit depends_on can capture a dependency that no expression makes visible. It shouldn't replace expressing ordinary data relationships clearly.

Across separate Terragrunt units, a dependency block reads another unit's outputs. Planning or applying one unit doesn't mean its upstream gets deployed first. Multi-unit orchestration and independent Atlantis projects each need their own ordering model. Terragrunt's block reference provides the relevant semantics.

One of our older guides implied that a plain single-unit terragrunt apply would apply its dependencies first. I'd fix that example in a living guide. Something being written in a team document doesn't make it more authoritative than how the tool actually behaves.

So a worked dependency example should cover two cases: consuming an output that's already deployed, and changing the upstream output together with its consumer. The reader needs to see why the second case may need staged plans and applies.

Style guidance should improve the next review

Our Terraform style guide aimed to keep code consistent and readable across modules. It covered identifiers, indentation, argument alignment, blank lines, comments, variable descriptions, and outputs. That pays off when an engineer moves between components that different people maintain.

Formatting tools handle most of the mechanical layout. Human guidance is better spent on design choices: which settings should be variables, which defaults are safe, what a module promises, and how an output becomes a dependency for another component.

A clear variable declaration beats a clever expression that takes minutes to decode:

hcl
variable "environment" {
  description = "Deployment environment used for naming and metadata."
  type        = string
}

variable "enable_metrics" {
  description = "Expose the application's supported metrics endpoint."
  type        = bool
  default     = true
}

The guide around it should explain the operational reasoning behind the default. Demanding a description field and accepting "enable metrics" as enough documentation misses the point.

Style guides age, too. Our older guide had outdated syntax and credential examples I wouldn't copy into a current onboarding page. New examples should use supported types and the team's current credential mechanism. Terraform's current style guidance is a useful reference, though repository conventions still need to describe the workflow you actually run.

Recovery guides need evidence before actions

The happy path is only half the documentation. A platform gets much easier to run when a failed plan, a locked project, or a half-finished apply has a clear way back.

A runbook should start with the symptom and the evidence to check. Then it should describe the decision and what the action is expected to do. A bare command without those conditions leaves the reader guessing when it's safe to run.

SymptomFirst evidence to inspectRecovery decision
No plan appearsWebhook delivery, project detection, changed-file coverage, service logsFix the triggering path before repeatedly issuing commands
Another pull request holds the projectAtlantis lock owner and operation statusCoordinate with the owner and release only stale coordination
Terraform reports a backend lockBackend lock identity and active execution logsEstablish whether a writer remains before considering lock recovery
Apply fails after some resources changeLast successful resource operations, current state, cloud-side statusReconcile with a fresh plan; do not assume rollback
DTE remains after cleanupCleanup run, namespace phase, finalizers, owner metadataInvestigate the deletion blocker and any external resources
Service is deliberately scaled downAvailability schedule and autoscaling configurationUse the documented wake path and account for the schedule

Atlantis project locks and Terraform backend state locks belong in separate branches of the runbook. Atlantis explains its coordination lock, and Terraform explains state locking. Removing either one isn't a fix for an operation that's still running.

The guide should also say when to bring in a second engineer. A routine replan and a state migration carry very different risks. Making that explicit lets people move fast on ordinary work and still recognize the cases that deserve another pair of eyes.

Keep documentation close to the implementation

Generated reference docs were part of the module workflow. terraform-docs kept README inputs and outputs up to date, and a table-of-contents tool kept long pages navigable. That made it less likely a new variable existed only in source code.

Generated docs can't explain an architectural tradeoff, a migration, or a recovery decision, though. I'd keep a short hand-written module purpose, a minimal example, operational assumptions, and upgrade notes right next to the generated reference.

For workflow guides, the authoritative examples should live next to the configuration they describe. If repos.yaml changes an approval requirement, the guide should change in the same review. If a cleanup job changes its schedule or label selector, the promised DTE lifetime should be updated with it.

A documentation pull request can also check examples against current tool versions. Pull out and exercise code fences where it's worth it, without pretending every illustrative fragment is a complete deployable stack.

Monitoring belongs in the guides too

A guide should connect a failure to the dashboard and logs that explain it. For our DTEs, ownership and age in Grafana gave engineers a practical way to find their environment. For Atlantis, the module's Prometheus integration gave a path to operation and process metrics.

I'd write down what each signal means. A count of DTE namespaces measures inventory, not whether applications are ready. A successful cleanup job should mean the deletion was verified, not just that a request went out. An Atlantis health endpoint shows the service is up, not that a particular Terraform apply worked.

The troubleshooting page should cover the common ways dashboards mislead too: a missing series, a missed scrape, duplicate collectors, or a service that's asleep on purpose. A graph is far more useful when you know what it's actually measuring.

It's also a good place to name owners. A dashboard with no responsible team still leaves the engineer wondering who to talk to next.

How I would roll out and maintain the guide set

Guides should be tested by using them, not just proofread. Here's how I'd roll out and look after a platform's documentation today.

  1. Choose the most common real task. Write the shortest complete path for a first reviewed change, with prerequisites, expected output, and links to deeper material.
  2. Pair with an engineer who did not build the workflow. Watch where they need additional context. Update the guide at the point where they stop rather than add a large unrelated FAQ.
  3. Add the highest-value recovery paths. Use actual support questions and known failure modes to prioritize runbooks.
  4. Connect references to source. Keep generated module tables, workflow snippets, and version requirements reviewable alongside their implementation.
  5. Assign maintenance ownership. Update guides when behavior changes, and review old examples before they become misleading onboarding advice.
  6. Measure whether the guide helps. Track repeated questions, first-change completion, and support effort if the team has the data. Do not equate page views with successful use.

What I'm after is shared ownership. Another engineer should be able to find the right unit, propose a change, understand the plan, and recognize when they need help. That's how documentation makes an infrastructure platform usable beyond the people who first built it.
