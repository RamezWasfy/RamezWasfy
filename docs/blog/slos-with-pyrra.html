SLOs with Pyrra, and the data behind the budget

We compared SLO tools to make reliability objectives easier to define and run. Pyrra fit our Prometheus-based platform, but going back over the implementation raised a more important question: did the queries and the history we kept actually support what the dashboard promised?

Begin with a user-facing question

Infrastructure health is useful context, but it isn't the same as a user journey working. A cluster can look healthy while an application returns errors. An application can serve requests while its background jobs fall far behind.

The SLO work gave us a way to describe acceptable service behavior over time, and a shared language for deciding when reliability work deserved attention. The goal was to make the conversation more concrete than "this service should be highly available."

A service-level indicator, or SLI, is the measurement. For an HTTP endpoint, that might be successful eligible requests divided by all eligible requests. A service-level objective, or SLO, sets a target and a window for that measurement. A service-level agreement, or SLA, is an external commitment. An internal SLO should guide engineering decisions; it shouldn't be called an SLA just because the percentages match.

What counts as eligible matters a lot. Which endpoints are in? Do client errors count as service failures? Are health checks excluded? Does a timeout before the request reaches the application show up in the denominator? I'd settle these with the service owner before choosing any tool.

Why we chose Pyrra at the time

Our comparison covered Pyrra, Sloth, and Google's slo-generator. After testing, we went with Pyrra because it had a usable interface and an operator that fit our existing Prometheus and Thanos stack. It meant less dashboard and recording-rule wiring for the team to maintain by hand.

That was a choice for that context, not a permanent ranking. Our comparison also described Sloth as inactive, but it has shipped releases since, so that claim shouldn't carry into a comparison today. Sloth's release history is the right place to check how actively it's maintained.

ToolWhat made it worth consideringWhat I would evaluate today
PyrraKubernetes-native objective definitions, generated rules, and an included UIVersion compatibility, rule output, query cost, UI access, and fit with our metrics backend
SlothA specification and generation workflow for Prometheus SLO rulesExisting GitOps workflow, generated alerts, available integrations, and operational ownership

These are evaluation criteria. I'm not claiming we tested every current feature back then. The project repositories describe where each one is today: Pyrra, Sloth, and slo-generator.

For a fresh decision, I'd implement the same availability and latency objective in each shortlisted tool, read the generated queries, and compare how an engineer would investigate a depleted budget. A feature checklist misses what it costs to understand the result in the middle of an incident.

We deployed Pyrra's API separately from its Kubernetes operator. The operator watched SLO resources and generated Prometheus rule resources, with RBAC granting the permissions it needed for those resources and their status. The API was pointed at a metrics query endpoint and an internal backend service.

The module pinned an older Pyrra version and ran each deployment with one replica. That's what we ran, not a version recommendation or a highly available setup. The rolling update settings also need to be weighed against how available the UI and controller should be.

The operator had generic rules turned on, which helped with shared dashboards. Generated rules still have to be evaluated, stored, and queried. A generator saves you repetitive authoring; it doesn't make recording rules free.

Here's a generalized availability objective in Pyrra's resource shape. The metric and selectors are illustrative; match them to the application's instrumentation and the installed CRD before applying anything:

yaml
apiVersion: pyrra.dev/v1alpha1
kind: ServiceLevelObjective
metadata:
  name: payments-availability
  namespace: monitoring
  labels:
    prometheus: platform
spec:
  target: "99.9"
  window: 30d
  description: Successful eligible payment requests
  indicator:
    ratio:
      errors:
        metric: http_requests_total{service="payments",environment="production",status=~"5.."}
      total:
        metric: http_requests_total{service="payments",environment="production"}

The example uses counter selectors and leaves the windowed calculations to the generator. The rule-selection labels have to match your Prometheus installation. Copying a label doesn't make a rule discoverable.

For latency, I'd define the share of eligible requests that finish under a chosen threshold, using histogram buckets. The threshold has to match a bucket that actually exists. A p95 dashboard helps with investigation, but it isn't a substitute for an event-based latency budget.

Correct the disagreement between prose and code

The old Pyrra guide described a 100 ms Grafana latency target, but its query selected the 500 ms bucket. The newer Grafana SLO definition also selected le="0.5". So the code supports a 500 ms threshold for that objective, not the 100 ms the prose described.

That definition used a 99% target over two weeks. It's separate from the illustrative payments objective above, which uses 99.9% over 30 days. Mixing the two would make a convincing but wrong story about what we built.

The availability indicator put server errors in the numerator and all selected responses in the denominator, with selectors scoped to the application and deployment. Before trusting the budget, I'd check that the total and error series describe the same population and that the labels don't accidentally merge unrelated environments.

This is exactly the kind of inconsistency a documentation review should catch. The target, window, metric, and eligible traffic belong together in one definition. If someone changes one of them, the explanation and the runbook should change in the same review.

A two-week objective needs two weeks of evidence

The old guide also described three days of local Prometheus retention. That's shorter than a two-week objective. A dashboard can still produce a number from whatever samples exist, but that number isn't a complete two-week budget.

The newer platform configuration pointed Pyrra at a Thanos querier. It included a Receive path for remote-written metrics and compactor settings for longer retention: 30 days for raw samples, longer for downsampled data. Those settings show intent. They don't prove the components were enabled everywhere, that object storage has unbroken history, or that every required series arrived.

The path that matters is Prometheus agents to Thanos Receive, then persisted blocks in object storage, with Store Gateway making stored blocks queryable through Querier. Receive also serves recent data. Store Gateway reads stored blocks; it isn't where a sidecar uploads to directly. Thanos documents Receive's ingestion and storage roles.

I'd check a full objective window at the same query endpoint Pyrra uses: earliest available samples, gaps, counter resets, duplicate replicas, external labels, and the generated rule history. Long object retention is necessary for long windows, but it doesn't prove coverage.

Downsampling needs care too. A long historical chart and an accurately rebuilt request budget are different requirements. I'd validate the exact counter and recording-rule queries against the resolution available for the window, instead of assuming a one-year retention setting keeps every short-window calculation intact.

Make the error-budget arithmetic inspectable

For an event-based 99.9% objective, the allowed failure fraction is 0.1%. With 200,000 eligible requests in the window, the budget allows 200 failures. With 160 failures, the observed success rate is 99.92%, 80% of the budget is used, and 20% remains.

The observed failure fraction is 0.08%. Divide that by the allowed 0.1% and you get a burn rate of 0.8 over the same window. A burn rate above one means the service is spending budget faster than the objective allows.

For a time-based 99.9% objective over 30 days, the allowance works out to 43.2 minutes. That's a helpful analogy, but an event-based request budget isn't automatically a downtime number. Traffic varies, and a partial failure can hit some requests while the service stays reachable.

If there were no eligible requests, the ratio tells you nothing about availability. If telemetry is missing, zero recorded errors isn't evidence of success. Both states should be visible, not turned green by default.

Separate a budget review from an urgent alert

The illustration shows a sample objective, remaining budget, and historical windows. The numbers are for teaching; it isn't one of our production dashboards. The lower table compares past windows; it doesn't simulate alerts evaluating at the same time.

A budget review asks how the service behaved over the objective window. An urgent alert asks whether someone needs to act now. For sustained failures, pairing a short and a long evaluation window catches fast budget burn without notifying on every brief blip. The short window confirms the problem is still happening; the long one shows the impact is sustained. Google's SRE Workbook explains this approach.

The alert needs a service owner, a severity, a runbook, a dashboard, and a way to find recent changes. Low-traffic services need deliberate handling: a handful of failures can dominate the ratio, while a minimum-volume condition can hide a real problem. For some services, a synthetic journey or a job-completion objective fits better.

I'd start with notification-only evaluation and compare alerts against known incidents before introducing any paging policy. What we built covers the objective definitions and the platform integration. I don't have measured on-call improvements from every generated alert.

Roll out one objective completely

I'd start with one service and one important user journey. Agree on the population and what counts as failure, inspect the metrics, choose a realistic target, and review the resource with the owner. Confirm the operator reconciles it and that the rule evaluator, Prometheus or Thanos Ruler, picks up the generated rules. A Prometheus agent that only forwards metrics doesn't evaluate rules.

Next, check history at the same endpoint the UI uses, trigger a known failure, and look at the numerator, denominator, budget, and alert state together. Include missing telemetry and an empty traffic window in that review. Write down what each state means and what the owner should do.

Only then would I expand to more services. A reusable manifest and dashboard are valuable once the first objective is well understood. Copying an unexplained target to every application just produces more configuration, not better reliability decisions.

Day to day, I'd watch reconciliation failures, rule evaluation errors, query latency, storage coverage, and notification delivery, and keep an eye on changes to metric names and labels. An instrumentation migration can break an objective even when the service itself is fine.

What this work taught me

The tool made the workflow easier to adopt. The engineering that lasted was getting the definition, the query, the history, and the response to agree with each other.

If I picked this project up again, I'd keep the reviewed-resource approach and the friendly UI, fix the inconsistent latency description, and make coverage checks part of the operating guide. An error budget is only useful when another engineer can explain where its number came from and what decision it supports.
