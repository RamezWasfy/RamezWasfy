Building a logging pipeline people can investigate

Getting logs into Splunk was only the start. The useful work was keeping context, making delivery failures visible, and turning searches into alerts with a clear owner and a sensible next step.

Start with the investigation

Production problems rarely start with a perfect query. Someone knows requests are failing, a deployment changed, or a background job stopped moving. They need to connect that symptom to a service, an environment, and a recent event without guessing which machine to look at.

In the infrastructure I worked on, logging covered several sources: Kubernetes applications, Linux services, and AWS delivery paths. They didn't share a format, retention needs, or audience. Treating everything as one unstructured stream would have pushed all that complexity into every investigation.

I think of this work as a contract between application teams and the platform. Applications provide stable fields and useful messages. The platform adds deployment context, delivers the events, controls access, and provides searches people can reuse. Both sides have a job to do.

The examples here rebuild that contract from our index guide, the newer Vector module, and the AWS Firehose configuration. Index names, service names, and addresses are generalized. The alert queries are worked examples, not our production saved searches.

Emit useful fields

A structured request event describes the service, environment, severity and correlation ID. Do not collect sensitive payloads by default.

JSON request event
service + environment + request_id

For container logs, Vector collected Kubernetes log events and enriched them before sending them to Splunk's HTTP Event Collector, or HEC. A separate optional source collected journald entries from selected systemd units. Keeping those apart mattered, because a container request log and a node service log need different context to be useful.

The newer module also had an internal metrics source and a Prometheus exporter, which let us watch the logging agent itself. Seeing application errors in Splunk doesn't prove the collector is healthy; a broken collector can stop sending exactly the evidence you'd need to diagnose it.

For AWS streams, we had a Firehose destination for Splunk, with configurable HEC acknowledgement, optional transformation, delivery logging, and an S3 backup mode. That was its own delivery path, and it should be investigated as one. Don't assume every AWS event went through the Kubernetes agent.

Preserve structured data without losing plain text

The Vector transform tried to parse each application message as JSON. If that worked, the parsed object went into a structured field. If not, the original text stayed available. That's a handy property during a migration: applications can move to structured logging without making older services unreadable overnight.

A generalized application event might look like this:

json
{
  "level": "error",
  "service": "payments",
  "environment": "production",
  "request_id": "sample-request-04",
  "event_type": "http_request",
  "status": 503,
  "duration_ms": 820,
  "message": "Upstream payment provider unavailable"
}

The original transform wrapped the parsed message in a structured envelope, so in a real search fields may be nested, like log_processed.status. The queries below assume a search-time normalization step that exposes the example fields at the top level. Check that normalization against real events before any search becomes an alert.

I like to keep the field contract small. Service, environment, severity, event type, and a correlation ID answer most first questions. Kubernetes namespace, pod, container, node, and cloud context then tell you where the event came from. A request ID is great in logs and usually a bad metric label, because every request creates a new value.

Sensitive data needs its own decision. Request bodies, credentials, payment details, and customer data shouldn't be collected by default for debugging. Redacting at the application boundary is much easier to reason about than hoping search permissions downstream make unnecessary collection acceptable.

Indexes and sourcetypes solve different problems

Our index registry separated data by purpose and access, and flagged legacy indexes that were being retired. An index is a storage and access boundary. A sourcetype describes the event format and how to parse it. Neither should be picked just because a team likes the name.

The Vector config let a Kubernetes annotation override the sourcetype, including separate overrides for stdout and stderr. Without one, it used a Kubernetes application default. In a generalized example, an application chart could carry:

yaml
spec:
  template:
    metadata:
      annotations:
        logs.example.com/sourcetype: payments:json

That shows the annotation contract; I've left out the real annotation prefix. It should be a documented choice with known parsing behavior, not a free-for-all for inventing formats.

The Vector sink didn't set an index explicitly. So index selection also depended on HEC token defaults and Splunk-side configuration. It would be wrong to say the sourcetype annotation picks the destination index or grants access to it.

For a new service, I'd confirm the destination index, which indexes the token can write to, the parsing rules, retention, and who's allowed to search the data. I'd also check whether a legacy index can stop receiving events before retiring its searches and dashboards.

Make delivery a monitored dependency

The newer module used separate Kubernetes and Linux HEC tokens, passed in through secret references, which gave the two streams their own configuration boundaries. Secret references avoid hardcoding, but Terraform state, Kubernetes permissions, token rotation, and collector access still need protecting.

The Kubernetes sink used HTTPS and compression. For Firehose, the module exposed S3 backup, encryption, compression, and buffering settings. Read those in context: an S3 buffering interval says nothing about end-to-end delivery latency to Splunk.

We also had CloudWatch alarms on log subscriptions: delivery errors over a short window, and no forwarded events over a longer one. Both sent alarm and recovery notifications. But their missing-data policy treated absent samples as not breaching, which is a real gap when the failure is telemetry disappearing completely.

A stronger setup would combine delivery errors, collector restarts, buffer pressure, and event freshness with a synthetic heartbeat: send a harmless, uniquely identifiable event on a schedule and check that it becomes searchable within a set delay. That's a check I'd add, not one I can say we had deployed.

Search narrowly, then add context

A good first search pins down the index, service, environment, and time range. Broad searches are slower, cost more to run repeatedly, and are harder to read. Splunk's spath can pull out JSON fields when needed; the exact path depends on whether the collector kept a nested envelope. Splunk documents the extraction behavior here.

For the normalized example schema, a quick investigation might start with:

spl
index=application_logs environment=production service=payments
earliest=-15m latest=now
| stats count by level

Then look at the raw events for one request separately:

spl
index=application_logs environment=production service=payments
request_id="sample-request-04" earliest=-15m latest=now
| table _time level status duration_ms message

The first search gives you aggregates. The second keeps the individual events. A chart of severity counts helps you get your bearings, but it can't replace the request-level sequence, or a trace when several services are involved.

For saved searches, I'd write down the expected field names, which sources are covered, the time window, and the owner. A query that depends on a field only half the services emit can give a confident-looking answer built on incomplete evidence.

Single conditions and composite conditions

A single-condition alert makes sense when one signal already means something. A batch job that emits a terminal failure event, for example, may need attention without waiting for an error percentage. A count-based HTTP example is less precise, but it's a reasonable starting point:

spl
index=application_logs environment=production service=payments
event_type=http_request earliest=-5m latest=now
| stats count(eval(status>=500 AND status<600)) AS failures
| where failures>=20

That threshold is just an illustration. It assumes one logged event per request and complete collection. Twenty failures could be serious at low traffic and noise at very high traffic. For user impact, a metric-based availability SLI is often the better primary signal, with logs supplying the diagnostic detail.

A composite condition can combine error rate, enough volume, and a relevant dependency symptom, within one service and window:

spl
index=application_logs environment=production service=payments
event_type=http_request earliest=-5m latest=now
| stats count AS requests
    count(eval(status>=500 AND status<600)) AS failures
    count(eval(dependency_error="timeout")) AS timeouts
| eval error_rate=100*failures/requests
| where requests>=100 AND error_rate>=2 AND timeouts>=10

"Composite" here just means several conditions in one search. It isn't an AWS composite alarm, and I'm not claiming Splunk Enterprise Security correlation searches were installed. Those are different mechanisms.

Correlating conditions makes an alert more specific, but it can also hide failures. If the provider starts returning instant errors instead of timeouts, that last condition could suppress a real incident. I'd keep the user-impact signal independent and use the dependency condition for a diagnostic alert or extra context. Test both the matching and non-matching failure cases before turning on notifications.

Control repetition without hiding a new incident

A saved search is more than its SPL. Its schedule, search window, trigger condition, and suppression policy decide what people actually receive. Overlapping windows can rediscover the same event, and delayed ingestion can make an event show up after the evaluation that should have caught it. Suppression should key on stable service and environment fields, with an expiry so a later incident can notify again.

Splunk supports custom trigger conditions and throttling. They're useful, but they don't establish who owns the incident or prove recovery. A recovery search, a metric alert, or the incident workflow has to define how the condition closes. Trigger conditions and throttling are documented separately.

The notification should say what crossed the threshold, over what window, which service and environment are affected, and who owns the next step. A link to the exact search, a service dashboard, and a short runbook beats a generic "errors exist" message every time.

Roll out with evidence and a cost boundary

I'd introduce a new source or alert in stages. First, look at representative events and parsing failures in a non-production environment. Then run the search without notifications, compare it with service metrics and known incidents, and pick a threshold together with the owner. Finally, turn on a narrow notification route and review what it actually sends.

Cost control starts with knowing daily ingestion by source, service, and severity. High-volume debug streams, repetitive health checks, and duplicate forwarding are worth a look. Audit evidence needs its own retention and access rules; dropping security events to shrink an application logging bill would be a bad trade.

What matters in the end is an investigation path that holds up on a bad day: useful events, known delivery behavior, scoped searches, and alerts someone can act on. That's the part of a logging platform I value most.
