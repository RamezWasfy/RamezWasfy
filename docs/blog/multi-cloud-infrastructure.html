One reviewed infrastructure workflow for AWS and GCP

Why we picked Terraform, Terragrunt, and Atlantis, how we organized state and reusable modules, and how we kept an eye on the whole workflow with Prometheus and Grafana.

At CLARK, I worked on infrastructure across AWS and GCP. I designed a dedicated infrastructure workflow and led the migration of our infrastructure code into the repository it managed. The goal was practical: an engineer should be able to propose a change, see what it does, get a real review, and apply it through a predictable process.

AWS was our main cloud; GCP ran a few specific services. We didn't try to hide the differences between them. An AWS account and a GCP project have different identity and resource models. What we wanted to standardize was how people worked with infrastructure.

The design had four layers. Terraform described resources. Reusable modules captured patterns we'd settled on. Terragrunt wired those modules to environments and dependencies. Atlantis tied execution to pull-request review. Guides and checks around it made the workflow usable by the rest of engineering.

The problem before a centralized workflow

The tricky part of infrastructure collaboration is usually the gap between the code in Git and the command someone actually runs. When people plan and apply locally, the person at the keyboard holds a lot of context: which credentials they used, which directory they were in, which tool versions they had, and whether the output they pasted still matches the latest commit.

A reviewer can read an HCL diff, but the diff doesn't show every consequence. A small input change can replace a resource, change permissions, or ripple into a dependent stack. The plan needs to be visible where the review happens.

Our internal decision guides named repeated manual steps, review quality, coordination, and auditability as the reasons to adopt Atlantis. After that, we pointed engineers to the centralized workflow and discouraged local applies. Those are the problems the process solved. I'm not going to dress them up as a story about a particular outage I can't point to.

Automation didn't remove the need to understand a change. It gave that understanding one consistent place to happen.

Give each tool a narrow responsibility

Terraform expressed the desired resources and worked out the provider-level change. Modules described patterns like networking, Kubernetes services, or a platform component, each with clear inputs, outputs, and compatibility expectations.

Terragrunt was the composition layer. It cut down repeated backend and provider setup, loaded contextual inputs, picked the module source, and read outputs from the units it depended on.

Atlantis handled collaboration and execution. It mapped repository changes to projects, ran the configured plan workflow, posted the result, and let approved changes be applied through pull-request commands.

Follow one infrastructure change

Choose a provider and inspect each step. The review process is shared; provider configuration remains explicit.

Change a unit

A leaf unit selects a released module and declares environment inputs. Its path identifies the provider and deployment scope.

AWS: account / region / environment / component
GCP: project / region / environment / component

Keeping those jobs separate made debugging much easier. A wrong module input is a different problem from a bad project mapping or a missing cloud permission, and you want to be able to tell which one you're looking at.

Why Terragrunt was useful for our repository

The infrastructure tree had several dimensions: provider, account or project, region, environment, and component. Copying the same backend and provider blocks into every component would have meant a lot of repeated configuration.

Terragrunt let us centralize the common behavior while keeping context next to the deployment. Our AWS hierarchy had common, account, region, and environment variable files. Provider generation folded metadata like owner, cost center, and environment into resource tags.

A generalized layout looks like this:

text
infrastructure/
  aws/
    terragrunt.hcl                 # shared AWS configuration
    common.tfvars
    accounts/
      development/
        account.tfvars
        eu-central-1/
          region.tfvars
          staging/
            environment.tfvars
            network/terragrunt.hcl
            application/terragrunt.hcl
  gcp/
    terragrunt.hcl                 # shared GCP configuration
    common.tfvars
    projects/
      analytics/
        project.tfvars
        europe-west1/
          staging/
            dataset/terragrunt.hcl

terraform-modules/
  modules/aws/
  modules/gcp/
  stacks/

Shared configuration without hiding deployment scope

The directory structure made provider and environment scope obvious. Shared configuration generated the backend and provider wiring; each leaf unit picked a module and supplied its inputs.

Here's a reconstructed leaf unit, with generic paths and a placeholder module source:

hcl
include "provider" {
  path = find_in_parent_folders("terragrunt.hcl")
}

terraform {
  source = "git::https://example.com/engineering/terraform-modules.git//modules/aws/application?ref=v2.4.1"
}

dependency "network" {
  config_path = "../network"
}

inputs = {
  environment = "staging"
  vpc_id      = dependency.network.outputs.vpc_id
  subnet_ids  = dependency.network.outputs.private_subnet_ids
}

What I like about it is that the application config states its own requirements while reusing shared conventions. A reviewer sees the module version and the upstream relationship in one place.

Indirection has a cost, though. Someone reading the leaf file also has to understand the included configuration and input precedence. That's why the hierarchy needed a guide and worked examples. Less duplication shouldn't mean hiding everything behind inheritance nobody explains.

Dependencies are a graph, not an ordering wish

A dependency block reads outputs from another Terragrunt unit. It doesn't mean applying one unit also deploys its upstream. When both network and application change, the workflow needs a deliberate order and fresh outputs.

For a multi-unit operation, dependency-aware orchestration can follow the graph. For independent Atlantis projects, the order has to live in the automation or be handled with staged changes. Turning on parallel plans and applies doesn't give you safe ordering. Terragrunt's HCL reference describes these blocks.

I prefer small changes that set up the upstream contract first and then update the consumers. The plan is easier to read, and you don't discover a missing output halfway through a big rollout.

State design mattered as much as directory design

Our AWS configuration kept Terraform state in an encrypted S3 backend, with a key derived from the unit's location and a DynamoDB table for locking. The GCP configuration used the same central S3 backend, under a separate GCP state-key prefix. Which cloud manages the resources and where the state lives were two separate decisions.

That's a specific detail of how we built it. It would be wrong to say all GCP state lived in GCS just because GCP resources were involved.

This simplified version of the pattern leaves out account numbers, bucket names, and keys:

hcl
remote_state {
  backend = "s3"
  config = {
    bucket         = "example-infrastructure-state"
    key            = "aws/${path_relative_to_include()}/terraform.tfstate"
    region         = "eu-central-1"
    encrypt        = true
    dynamodb_table = "example-terraform-locks"
  }
}

It explains our design; it isn't a recommendation to copy the backend config into a new project unchanged. Check locking options and credential mechanisms against your Terraform version and current platform standards.

Giving each unit its own state narrowed the blast radius of an operation and made ownership easier to manage. It didn't make the dependencies go away. State can contain sensitive values, so access to backend data needed tighter control than access to ordinary source code.

Because the key depended on the path, renaming a directory could also mean moving state. Moving a unit needed a state migration plan; it wasn't just tidying up files.

Why Atlantis, and what an ordinary change looked like

Atlantis put the plan next to the code and the conversation. An engineer opened a pull request, the affected projects planned, reviewers read the proposed changes, and an approved apply used the saved plan. Our documented workflow also merged automatically after a successful apply.

A normal change went like this:

  1. Create a branch and change the relevant unit or module version.
  2. Run local checks and inspect the diff before opening the pull request.
  3. Let Atlantis produce the plan for the affected projects.
  4. Review additions, modifications, replacements, and deletions, including dependency impact.
  5. Obtain the required approval and a mergeable pull request.
  6. Apply through Atlantis, inspect the result, and verify the resulting service behavior.

The server-side repository config required approved and mergeable for both apply and import. It used a custom Terragrunt workflow, with pre-workflow hooks that selected tooling and generated the project configuration.

A generalized excerpt shows the core behavior:

yaml
repos:
  - id: github.com/example/infrastructure
    apply_requirements: [approved, mergeable]
    import_requirements: [approved, mergeable]
    workflow: terragrunt

workflows:
  terragrunt:
    plan:
      steps:
        - run: terragrunt plan -input=false -out=$PLANFILE
        - run: terragrunt show -json $PLANFILE > $SHOWFILE
    apply:
      steps:
        - run: terragrunt apply -input=false $PLANFILE

Applying the saved plan ties the operation to exactly what was reviewed. If the code, the relevant state, or a dependency changes, regenerate and re-review the plan instead of assuming the old one still holds.

We also supported imports and policy workflows. Both are powerful. An import needs a clear resource address and the existing resource's identity, and the next plan should confirm the configuration really matches the imported object. Policy evaluation needs to read the actual plan and produce a result reviewers can make sense of.

Our server config had a policy-check stage over plan JSON, with policy owners. Separate tooling turned IaC scanner findings into Atlantis policy results. Having a scanner in the image doesn't prove every repository enforced every policy, though. What the configured workflow actually ran is what counts.

Project discovery and change impact

A script discovered Terragrunt projects and generated atlantis.yaml. It created one project per discovered directory, named the workspace after its path, and set autoplan rules for Terraform, HCL, templates, and supporting files. It also turned on parallel plan and apply.

Generating the project list meant adding a unit didn't require hand-editing config. But discovering projects and working out change impact are different problems. A generator can find a unit without knowing that a shared parent config just changed how it behaves.

Changing a shared account input or provider template, for example, can affect many leaf projects, and narrow file globs on each leaf may miss that. Likewise, a change in the module repository doesn't reach a pinned consumer until its reference is bumped.

For a new rollout, I'd test the change matrix explicitly: a leaf edit, a parent input edit, a shared provider edit, a module version bump, a new directory, and a dependency output change. Each case should plan exactly the projects you expect. I'd also cap concurrency instead of assuming every cloud API and backend can take unlimited parallel work.

Two locks, two different recovery decisions

Atlantis project locks coordinate pull requests working on the same project. Terraform backend locks protect state during an operation, when locking is enabled and supported. They're related, but they're not the same lock. Atlantis documents project coordination, and Terraform documents backend state locking.

That difference matters when something gets stuck. If an old pull request holds a project lock, find that pull request and make sure nothing is still running before releasing it. If the backend reports a state lock, find out who's writing and what state they're in before touching anything.

Unlocking doesn't prove the previous apply finished or rolled back. A failed apply may already have changed real resources. Recovery means reading the execution logs and current state, then producing a fresh plan.

Our Terragrunt config also had backend locking turned off for plan operations. In a new implementation I'd revisit that on purpose rather than assume every command had the same locking guarantees. Documentation should describe the settings you actually run, not just what the tools are capable of.

How we connected Prometheus and Grafana

Our Kubernetes Atlantis module exposed Prometheus metrics at /metrics, with a ServiceMonitor that selected the Atlantis service and scraped its named HTTP port. It was a concrete integration in the module, not a vague "we had monitoring somewhere."

The shape was:

text
Atlantis /metrics
       |
       v
Kubernetes Service -> ServiceMonitor -> Prometheus
                                           |
                              +------------+-----------+
                              |                        |
                         Grafana views             Alert rules

A generalized monitor definition looks like this:

yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: atlantis
  namespace: platform
spec:
  selector:
    matchLabels:
      app: atlantis
  endpoints:
    - port: http
      path: /metrics

Prometheus also has to select that ServiceMonitor and be able to reach the endpoint. Creating the custom resource on its own doesn't prove anything is being scraped.

Atlantis exposes metrics for operation success, errors, and timing. Its metrics reference lists the available families. I'd build Grafana views around operation errors and durations, process health, and the Kubernetes workload, taking exact metric names and types from the running version rather than a dashboard copied from someone else's install.

A simple health panel:

promql
up{job="atlantis"}

The job label has to match your scrape configuration. For a version that exposes the documented autoplan counter, a useful error panel is:

promql
increase(atlantis_cmd_autoplan_builder_execution_error[1h])

These are example panels; I don't have our original dashboard expressions to show. For durations, check whether the metric is a histogram or a summary before writing a percentile query. A histogram query pasted over a summary gives you misleading or empty results.

I'd keep automation health separate from infrastructure health. A successful Terraform apply doesn't mean the application is healthy. And a crashing Atlantis pod can block infrastructure changes while production keeps serving traffic just fine. Grafana should make both situations easy to read.

Useful signals include pod restarts, memory pressure, pending jobs, failed plans and applies, cloud permission failures, and how long engineers wait for a usable plan. Lock inventory and lock age may need extra instrumentation; don't assume the default metrics have them.

The platform could also scale Atlantis down on a schedule with KEDA, so time matters. A service that's asleep on purpose shouldn't raise the same alert as one that disappears during hours it's supposed to be up.

How I would phase the migration

I led the infrastructure-code migration, but I'm not going to invent a detailed historical calendar for it. Here's the plan I'd follow for the same design today.

  1. Inventory the existing units. Record state location, provider identity, tool versions, dependencies, owners, and which resources are already managed. Avoid importing or recreating resources blindly.
  2. Establish the repository contract. Define the provider hierarchy, state-key rules, module references, tagging, and the boundary between shared configuration and leaf inputs.
  3. Pilot a small non-production unit. Verify identity, remote state, project discovery, approval requirements, saved-plan application, and a no-change rerun.
  4. Exercise shared changes and recovery. Test parent-input impact, dependency order, stale plans, lock conflicts, and a controlled failed operation before broad migration.
  5. Move units in manageable groups. Preserve state ownership, stop duplicate writers, review plans for unexpected replacement, and keep a documented rollback or handback path.
  6. Measure and support adoption. Watch workflow errors and latency, update guides from real questions, and expand once another engineer can complete the normal path unaided.

What we ended up with was one way of working across two cloud providers, without pretending they were the same. The tools earned their place because each had a clear job, and because review, state, module versions, monitoring, and recovery were treated as parts of a single workflow.
