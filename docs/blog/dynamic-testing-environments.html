Building dynamic testing environments developers could actually use

How we used Jenkins, Helm, and EKS to turn a feature branch into a testing environment anyone could open, and then made ownership, monitoring, cleanup, and cost part of the same workflow.

At CLARK, I helped implement and support our dynamic testing environments, or DTEs. The problem started with everyday development. Running the application locally meant setting up a big stack, getting its dependencies into a usable state, and finding enough resources on a laptop to build and run it all. That was hard, and some machines just weren't up to it.

Sprint reviews had a second problem. A developer could explain a feature, but showing it to someone usually meant asking them to reproduce the setup or juggling access to a shared environment. A change deserved a place where teammates could open a link and try it.

DTEs gave us that place. A developer picked the versions they were working on, created an environment in our development cluster, and shared its URL for testing or a sprint demo. Making that repeatable was useful. Making each environment observable, with a deliberate end of life, is what made the platform sustainable.

What the platform needed to solve

A developer should be able to answer a few practical questions without waiting for a CloudOps engineer: Which branch is deployed? Which services are included? Where's the application? Did the smoke tests pass? How long will the environment stick around?

The infrastructure team had its own questions: Who owns it? Is it ephemeral or persistent? How much cluster capacity is it using? Did cleanup run? Is anything still left after the namespace was deleted?

Both sets of questions shaped the design. Provisioning alone would only have covered the first few minutes of an environment's life.

BeforeWhat the DTE workflow changed
Each developer had to make a large application stack work locallyA repeatable remote environment reduced dependence on laptop capacity and local setup
Demonstrating a branch required coordination or another person's setupThe developer could share an application URL for a sprint review or feature discussion
Temporary environments depended on someone remembering to remove themEphemeral metadata and a scheduled Jenkins cleanup job made removal an explicit platform responsibility
An environment name did not tell us enough about ownershipNamespace metadata connected the environment to its owner, branch, and build
A list of running workloads did not explain why they were thereGrafana showed running DTEs, ownership, and age

DTEs didn't replace every local development task. They gave people a dependable path for integration testing and demos when running the whole application locally was expensive or awkward.

Architecture and the developer journey

We reused tools we already ran: AWS EKS to run the workloads, Jenkins to orchestrate, and Helm to package the application and its dependencies. Each environment got its own namespace in a shared development cluster.

The workflow went through more than one generation. The bigger application pipeline took a branch, tag, or commit, plus service switches, database setup, smoke-test choices, and Docker cache settings. A later Helm-based path took an application image tag and a chart version, created the namespace, deployed the chart, and saved the namespace and hostname in a dte.yaml artifact.

That history matters. There was never one universal pipeline that magically understood every application. The platform handled the common lifecycle, while the deployment inputs still reflected what each application needed.

Requesting from Jenkins or a GitHub pull request

Jenkins was the form-based entry point: choose the application and source version, pick the supported deployment options, and let the pipeline hand back the environment details. Parameter names changed between generations, but the journey felt the same.

There was a GitHub entry point too. Once the required CI checks passed, a developer could comment /create dte on the pull request. The request and the result stayed in the PR conversation, so the preview showed up right where reviewers were already talking about the feature.

Make the input contract small and explicit

The Helm path made the application image and the chart version two separate choices. That kept a clear line between the code under test and the packaging used to run it. A stable namespace and hostname derived from the branch made the environment easy to find again.

Names needed cleaning up, because Git branch names don't always fit Kubernetes naming rules. The pipeline normalized them before creating anything. If I built it again, I'd also add a short branch hash, so two branch names that normalize to the same string can't collide.

The later pipeline used Helm's install-or-upgrade behavior, atomic: true, a one-hour deployment timeout, and a shared helper with tests enabled. Atomic mode helps when a Helm operation fails, but it can't roll back every database migration or external side effect. The application still needs its own clear failure model.

The final artifact connected the Jenkins run to something a developer could actually use:

yaml
# Reconstructed example of the archived deployment details.
namespace: dte-payments-feature-checkout
hostname: dte-payments-feature-checkout.preview.example.com

Every deployment should end with a handoff like this, instead of leaving someone digging through logs for an ingress address.

Metadata was part of the platform contract

Namespace metadata told us whether an environment was ephemeral or persistent. To be precise, the environment type was a Kubernetes label, which made it easy for cleanup jobs to select namespaces. The full owner identity and build context lived in annotations. The newer creation path also added cleaned-up owner and branch labels for discovery.

This generalized manifest shows the same split:

yaml
apiVersion: v1
kind: Namespace
metadata:
  name: dte-payments-feature-checkout
  labels:
    platform.example.com/dte: ephemeral
    platform.example.com/owner: engineer-a
    platform.example.com/application-name: payments
  annotations:
    platform.example.com/owner: engineer-a@example.com
    platform.example.com/branch: feature/checkout
    platform.example.com/commit: example-commit-reference
    platform.example.com/build-url: https://ci.example.com/job/dte/123
    platform.example.com/creation-channel: Jenkins

The keys are stand-ins for our internal ones. What matters is the contract: automation selects by type, engineers can find an owner, and every environment traces back to the build that created it.

The shared namespace helper also refused reserved names and created role bindings for the right engineering groups. That stopped a DTE request from casually targeting something like default or kube-system.

A namespace is an organizational boundary, not full security isolation. Workload permissions, network policies, secret access, and test data all need their own controls. Kubernetes describes namespace scope. In particular, a development environment shouldn't get production secrets just because the chart happens to accept them.

Ephemeral and persistent environments had different promises

Ephemeral was the default, and it suited short testing sessions. Developers used the environment during the day, and an end-of-day Jenkins job removed the eligible ones. That replaced a cleanup process that would otherwise rely on everyone remembering what they'd created.

Persistent environments covered other needs: an investigation, a review that ran over several days, or testing that had to survive the nightly cleanup. Removing a persistent environment stayed the owner's job. The cleanup workflow reminded owners about older persistent environments instead of deleting them by default.

The expiry job ran in the 22:00 hour, Europe/Berlin time, using Jenkins' hashed scheduling, and by default it selected environments older than six hours. Both details matter. An environment created just before the nightly run could survive until a later run. This was a scheduled sweep, not a controller deleting things exactly six hours after creation.

What the nightly job would select

Change the environment type and age. By default, the nightly job selected ephemeral DTEs older than six hours.

Namespace metadataAge > 6 hours?Select for deletion

An eight-hour-old ephemeral environment is selected for deletion when the nightly job runs.

This is a selection rule at a scheduled run, not a strict six-hour TTL. Persistent deletion is disabled by default.

The logic was roughly:

text
cutoff = current_time - configured_age_threshold

for environment in ephemeral_environments:
    if environment.created_at < cutoff:
        request_namespace_deletion(environment)

for environment in persistent_environments:
    if environment.created_at < cutoff:
        if explicit_persistent_deletion_enabled:
            request_namespace_deletion(environment)
        else:
            remind_owner(environment)

wait_for_requested_deletions
report_cleanup_failures

The job had an explicit cutoff, separate switches for deleting ephemeral and persistent environments, and a dry-run option for its shell operations. It also sent a notification when it failed. Dry run didn't guarantee every side effect was suppressed, though; notifications needed to be checked separately.

There was also a cleanup path for merged branches, so finished work didn't have to wait for the next nightly sweep. Different workflow generations used different namespace conventions, so matching a branch to its environment has to be checked carefully during migrations.

Cleanup can fail after the deletion request succeeds

The job asked for each namespace deletion without waiting, then waited for all of them to finish. That way it could work through several candidates and still check that removal actually completed.

A namespace stuck in Terminating is an operational problem, not a finished cleanup. Finalizers, unavailable controllers, or external resources can keep it around. Recovery should start by looking at what's blocking it and which controller owns it. Stripping a finalizer you don't understand can leave an external resource behind.

I'd also make cleanup idempotent: if a merge-triggered job already removed an environment, the nightly job should treat that as normal. Two lifecycle paths should end up at the same result.

What we monitored with Grafana and Prometheus

Our Grafana DTE view answered the basic questions: how many environments were running, who owned them, and how long they'd been up. We went further than that, though, and connected the inventory to resource allocation, estimated cost, readiness, and application capacity.

There were two views. Overview looked across the whole DTE fleet. Details zoomed into one namespace. A developer could go from finding their environment to inspecting the resources and application behavior inside it.

Overview: inventory, ownership, resources, and cost

The Overview dashboard had an Active DTEs stat, hourly cost by owner, CPU and memory request and usage tables, an hourly resource-cost time series, and an environment inventory table.

The inventory showed namespace, owner, persistence type, age, a readiness signal, and estimated cost. Each row linked to the environment, its details, and a Jenkins job to terminate it. That made the dashboard a real starting point for operations, not just a wall of charts.

Its namespace variables understood both the newer environment-type labels and the legacy DTE labels. That's a small, concrete example of monitoring keeping up with a platform migration: older environments shouldn't vanish from view just because an earlier creation path wrote their metadata.

Details: follow a namespace into its application

The Details dashboard had CPU and memory time series, network receive and transmit rates, pod information, and platform ingress routes. For the Ruby application it also showed Puma worker counts, running and maximum threads, thread-pool capacity, and request backlog.

Those panels helped separate a resource problem from an application-capacity problem. A namespace and its pods could look fine while requests waited for worker threads. The other way around, a pending or unready deployment could explain a broken preview long before application metrics meant anything.

The dashboard's information panel linked to the application, its branch, and the termination job. That tied diagnosis to the version under test and to whoever owned its lifecycle.

How the queries worked

These examples come from the real panel expressions, with generic label keys and server selectors. The query inspector above includes all fourteen panels that carry queries. Custom metrics like namespace:cost_dollar:sum and container:memory_usage_requests:percent came from recording rules; they don't exist out of the box in a kube-state-metrics install, and you'd need their definitions to reproduce the panels.

The age query compared the namespace creation timestamp with Prometheus time and converted the result to hours:

promql
(time() - avg by (namespace) (
  kube_namespace_created{
    prometheus_server="prometheus.example.com",
    namespace=~"${dte_namespaces}"
  }
)) / 3600

The owner-cost panel grouped each namespace's allocation rate by the owner annotation:

promql
sum by (annotation_platform_example_com_owner) (
  namespace:cost_dollar:sum{
    prometheus_server="prometheus.example.com",
    namespace=~"${dte_namespaces}"
  }
)

Hourly resource cost added pod and persistent-volume allocation to load-balancer cost. The ALB term deduplicated by ingress group, so one shared load balancer wasn't counted again for every matching namespace:

promql
sum(pod:cost_dollar:sum{
  prometheus_server="prometheus.example.com",
  namespace=~"$dte_namespaces"
})
+ sum(pvc:cost_dollar:sum{
  prometheus_server="prometheus.example.com",
  namespace=~"$dte_namespaces"
} or vector(0))
+ sum(max by (annotation_alb_ingress_kubernetes_io_group_name) (
  ingress:alb_cost_dollar:sum{
    prometheus_server="prometheus.example.com",
    namespace=~"$dte_namespaces"
  }
) or vector(0))

The environment-cost panel multiplied the current hourly namespace rate by age. That's a fair estimate when the rate is stable, but it isn't the real historical cost. Scaling, different workload sizes, and shared-cost allocation can all pull the estimate away from the measured total.

The inventory's Healthy column subtracted ready replicas from desired replicas, per namespace. Zero meant no shortfall by that measure. Useful feedback, but it isn't a smoke test and doesn't promise every user flow works.

Read the metric semantics, not just the panel title

The Active DTEs stat counted time series matching phase="Active". Phase gauges can include zero-valued samples, so a tighter query would filter to == 1 before counting, and deduplicate collectors if needed. That's how I'd improve it, not how the dashboard was written.

The detail resource panels also mixed raw CPU rates, memory bytes, configured limits, and custom percentage series. Those shouldn't share one unexplained percentage axis. The explorer keeps CPU cores and memory MiB apart so the units stay clear.

To reproduce the metadata view, you have to configure which namespace labels and annotations get exported. kube-state-metrics documents its namespace metrics and allowlists. With several clusters, keep cluster identity in your aggregations and joins, not just the namespace.

Monitor the cleanup job itself

An age panel is a useful symptom, but it shouldn't be the only sign that automation has stopped. A proper monitoring setup would track the last successful cleanup, how many candidates were selected, how many deletions finished, failures, and namespaces still stuck terminating.

For a nightly job, the alert window should follow the schedule and leave room for a normal run. Alerting whenever an ephemeral namespace passes six hours would misdescribe how the system works. A better alert combines a missed cleanup run with environments older than the expected schedule boundary.

Persistent environments need an owner reminder and a review, not the same urgent alert as a broken cleanup job. The response should match the promise we made to developers.

Cost controls were built into the lifecycle

A separate cluster per feature would have meant a lot of repeated overhead. Namespaces in a shared EKS development cluster let the platform reuse capacity, networking, and cluster services. Charts declared requests and limits, so every workload had an explicit resource shape.

Automatic expiry dealt with abandoned workloads. Owner reminders made long-lived persistent environments visible. Showing owner and age in Grafana made the cost conversation concrete: we could point at an environment and ask whether anyone still needed it.

We also had weekend scale-down and scale-up jobs. The shutdown job paused KEDA ScaledObjects before setting Deployment replicas to zero, so the autoscaler wouldn't immediately undo the shutdown. The Monday job removed the pause and set the configured replica counts. It didn't restore an exact snapshot of the previous replicas.

On top of that, the shared namespace helper created a weekday sleep schedule for CronJobs unless keep-awake was turned on. In the configuration I looked at, that schedule suspended CronJobs and explicitly left Deployments alone. That's a separate control from the weekend Deployment shutdown.

All of this reduces workload activity. It doesn't remove EKS control-plane charges, persistent volumes, or every shared service cost. Node costs only fall when the cluster's capacity management can actually remove unused capacity. Kubecost was part of our wider Kubernetes cost visibility and helped connect namespace usage to the shared bill.

A fair cost comparison includes environment resource-hours, storage, build activity, and dependencies that stay around. It should also count the time developers spend on local setup and support. I wouldn't put a savings percentage on this without the billing and usage data behind it.

A practical implementation and rollout plan

If I built this platform again, I'd ship it in stages that keep the developer experience and the operational controls together.

  1. Pick one application and define its environment contract. Spell out required services, test data, image selection, URL access, and what persistence means. Check that a developer can do a realistic test and a sprint demo.
  2. Make the deployment reproducible. Pin images and charts where you can, normalize names, add ownership metadata, and return the namespace and URL as build artifacts.
  3. Add lifecycle behavior before broad adoption. Default to ephemeral, add the persistent escape hatch on purpose, run cleanup against a reviewed candidate list, and confirm deletion actually completes.
  4. Add the inventory dashboard. Show count, owner, age, type, and application health. Track successful cleanup separately from successful creation.
  5. Control shared capacity. Set workload resources, watch for contention, add quotas and network controls that suit the cluster, and make sure shutdown doesn't fight autoscaling.
  6. Grow through developer feedback. Add applications once their dependencies and failure modes are understood. Treat repeated setup questions and failed demos as product feedback.

The outcome that mattered was practical: engineers could test and show their work without rebuilding the whole application on every laptop. The engineering that lasted was the lifecycle around that convenience, from picking a branch to a dashboard row that eventually disappeared because cleanup had really finished.
