KEDA autoscaling starts with understanding the signal

We scaled application replicas from Prometheus signals, including CPU-related measurements and Puma thread usage. Turning it on was easy. The hard part was understanding what each signal meant, how KEDA and the HPA shared control, and what happened when the measurement broke.

Choose a signal that describes the bottleneck

A replica count is an operational decision. Too few replicas and requests wait. Too many and you pay for idle capacity, or overload a shared database without making anything better for users. A good autoscaling signal describes work that extra replicas can actually take on.

Our KEDA guide had two examples. A backend workload scaled on a CPU-related recording rule with a target of 50. An admin workload scaled on summed Puma thread usage, multiplied into percentage units, with a target of 30. Both set minimum and maximum replicas, fallback, polling, and separate scale-up and scale-down behavior.

That's a better story than "we enabled autoscaling." Different workloads needed different signals and different response policies. Below I walk through those decisions, correct a few things the older guide got wrong, and lay out the validation plan I'd use before rolling them out today.

KEDA works with the HPA

Follow the signal all the way to ready capacity

KEDA and the HPA have different roles. More desired replicas are not yet more ready capacity.

Measure the bottleneck

Check units, labels and the recording rule. A sum of ratios is not average utilization; a scaler query must return one result.

one aggregate signal
known denominator + population

The older guide said the HPA was limited to CPU and memory. That's incomplete: the HPA can use custom and external metrics too. KEDA adds the integrations and metric access for event-driven scaling, and normally creates and manages an HPA for each ScaledObject. Kubernetes documents the HPA's metric support and control loop.

For a Prometheus trigger, KEDA queries the configured endpoint and exposes an external metric that the generated HPA reads. The HPA then sets the workload's replica count within the configured bounds. Knowing that split tells you where to look when something goes wrong: a successful Prometheus query doesn't prove the HPA accepted the metric, or that new pods became ready.

I'd avoid having two independent HPAs control the same Deployment. Ownership of the generated HPA should be explicit, and if GitOps manages the replica field, make sure it doesn't keep resetting the autoscaler's decisions.

Inspect the recording rule before choosing a threshold

The backend example used a recording rule, not raw container CPU. Its query summed a CPU-usage ratio across the selected backend containers and multiplied by 100. The selector excluded a different workload so two scaling populations didn't get mixed together.

Before reusing it, I'd look inside the recording rule. What's the denominator: CPU requests, limits, or some other capacity estimate? Does it produce one series per container or per pod? What happens when a request is missing? A metric name with "ratio" in it doesn't answer any of that.

The Puma example also summed thread-usage ratios across the selected admin pods. A sum of ratios isn't average utilization. It can grow just because there are more replicas, even if each replica is equally busy. That can be fine for an aggregate signal read against a per-replica target, but you need to understand it before choosing the metric type.

Here's a normalized version of the original idea:

promql
sum(ruby_puma_threads_usage_ratio{
  namespace="payments",
  workload="payments-admin"
}) * 100

The selectors are generalized. In a real implementation, check which labels the exporter actually provides and whether they exclude unrelated pods, old deployments, and duplicate scrape sources. The scaler query has to return a single scalar or a one-element vector, not several independent series. The Prometheus scaler reference describes the query contract.

Understand AverageValue and Value

For a positive aggregate signal, a simplified AverageValue recommendation is the ceiling of the aggregate signal divided by the per-replica target. With a signal of 60 and a target of 30, that's two replicas, before bounds and control-loop behavior kick in.

With a Value target, the simplified recommendation scales the current replica count by signal divided by target. At two current replicas, the same 60 and 30 give you four. Those are very different answers from the same numbers.

Bounds are min1/max4 for this example. Static fallback is modeled after the failure threshold, not on the first missed query. Actual behavior depends on the installed KEDA version and HPA state.

The calculator is a teaching model. The real HPA also accounts for tolerance, missing measurements, readiness, stabilization, and scaling policies, so don't read its output as a full replay of the controller.

That's why I review the generated HPA next to the ScaledObject: the external metric name, target type, target value, owner reference, and actual status. A threshold that looks sensible in Grafana can produce a surprising replica count once a different metric type interprets it.

Keep the first manifest understandable

This is a generalized teaching example, not a copy of a production manifest. It uses a backlog signal because a per-replica target is easier to reason about that way. Our documented workloads used CPU-related and Puma signals; I'm not saying we ran a queue-backed payments worker.

yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: payments-workers
  namespace: payments
spec:
  scaleTargetRef:
    name: payments-workers
  pollingInterval: 60
  minReplicaCount: 1
  maxReplicaCount: 4
  fallback:
    failureThreshold: 3
    replicas: 2
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleDown:
          stabilizationWindowSeconds: 600
        scaleUp:
          stabilizationWindowSeconds: 0
  triggers:
    - type: prometheus
      metricType: AverageValue
      metadata:
        serverAddress: https://metrics.example.com
        query: sum(payments_worker_backlog{namespace="payments"})
        threshold: "30"
        ignoreNullValues: "false"

I've deliberately left authentication to the metrics endpoint out of the example rather than invent it. A real deployment should set it up through the supported authentication resources and secret references, then check that the scaler can actually reach the endpoint.

Setting ignoreNullValues to false is a deliberate choice: an empty query shows up as a problem instead of being quietly accepted. Whether that's right depends on what "no series" means for that metric: no work, or a broken observation path.

Stabilization and cooldown have different jobs

Our backend example used a slower scale-up stabilization window and a longer scale-down window. The admin example allowed immediate scale-up, capped how fast it grew, and used a much longer scale-down window. Those settings encode different assumptions about bursts and how costly it is to remove capacity too early.

The older guide also set a cooldown of 600 seconds with a minimum of one replica. KEDA's cooldown only applies to scaling back to zero. It isn't a general ten-minute delay for every change between one and several replicas; HPA behavior governs those nonzero transitions. Likewise, restoreToOriginalReplicaCount is about what happens when the ScaledObject is deleted, not about restoring the starting count after every scaling cycle. The ScaledObject reference explains these settings.

These distinctions belong in the runbook. Otherwise someone tweaks cooldown while chasing a scale-down problem and sees no effect, because the workload never reaches zero.

Treat fallback as a capacity decision

The original examples fell back to one replica after a few metric failures. That keeps the workload running when its metric source is down, but it isn't automatically a safe amount of capacity.

If the application was serving peak traffic on four replicas when the measurement failed, a static fallback of one could cut capacity at the worst possible moment. I'd choose fallback and minimum capacity from measured workload behavior, and check what fallback behavior the installed KEDA version actually supports before relying on it.

The failure plan should tell apart a valid zero, an empty response, a query error, an authentication failure, and a metrics backend that's down. A missing metric is a failure to observe. It isn't proof the workload is idle.

In the calculator, metric failure means the configured failure threshold has already been crossed. It shows the static fallback on purpose so you can see what it does to capacity.

Verify the entire path to ready capacity

The resource-view illustration shows a sample Prometheus trigger, the generated external-metric HPA, and consistent 60 divided by 30 arithmetic. It's a teaching image, not a screenshot from one of our clusters.

For a real rollout, I'd watch the ScaledObject's Ready, Active, and Fallback conditions; the HPA's current metric, desired replicas, and scaling conditions; and the Deployment's available replicas. Then I'd look at pod scheduling, readiness, restarts, and how long new capacity takes to do useful work.

Scaling pods doesn't conjure node capacity. Pending pods can mean requests that don't fit, too few nodes, quotas, or constraints. A node autoscaler helps, but its startup and disruption behavior become part of your response time. So do application startup and cache warming.

Finally, check shared dependencies. More replicas can mean more database connections or more retry traffic. A request-latency or queue-age signal can show that extra pods aren't actually relieving the bottleneck. Review the autoscaler together with the service's resource requests, connection limits, and user-facing indicators.

A rollout plan with deliberate failure tests

I'd start by running the query with autoscaling off and comparing it against known workload changes. Check its units and result cardinality, then work out recommendations from several historical points. Look at low traffic, a burst, and a period with missing samples.

Next, deploy a narrow non-production ScaledObject with conservative bounds. Check the generated HPA and run a controlled load increase. Note when the signal changed, when desired replicas changed, and when ready capacity actually helped. Then test scale-down once the load drops.

Then break metric access on purpose. Check how failures accumulate, when fallback applies, what happens to the replica count, and how the owner finds out. Restore access and watch it return to normal control. This is the validation process I'd propose; I don't have measurements like these from the original guide.

In production, start with one workload and keep a documented way to disable the ScaledObject and set safe capacity. Review deletion behavior before relying on it for recovery. A setting meant to restore an original count can surprise you if that count no longer fits current demand.

The cost benefit depends on the service outcome

Autoscaling can cut idle replicas, but fewer pods isn't the only measure of success. I'd compare latency, failures, throughput or queue age, time to ready capacity, node allocation, and dependency pressure across the rollout.

If a service runs fewer replicas but fails more requests or keeps cold-starting, the tradeoff needs another look. And if smaller pod requests leave the same nodes allocated, the billing benefit may be smaller than a pod-count chart suggests. I don't have a measured savings figure for this work, so I won't claim one.

What I value in this project is the explicit link between signal, capacity, and operating behavior. KEDA made the integration practical. Understanding the query and the failure path made it supportable.
