Giving GPU workloads an explicit scheduling contract

A GPU node is just expensive general-purpose capacity unless the platform makes its purpose clear. Our infrastructure defined a separate NVIDIA pool, and the application config added a small GPU setting that had to survive the whole deployment path.

Why a separate pool made sense

GPU work needs something an ordinary web application doesn't. Adding more CPU nodes can't satisfy a pod that needs an NVIDIA device. And if unrelated applications can land on GPU nodes, expensive capacity sits there doing no accelerated work.

Our EKS Auto Mode development cluster had a GPU pool next to the general-purpose one. It selected the g instance category, amd64 architecture, and on-demand capacity, and it carried a custom gpu-type: nvidia label and a nvidia.com/gpu=True:NoSchedule taint.

That's real configuration, and it describes the intended placement and capacity boundary. It doesn't tell you how busy the GPUs were or prove every workload used the pool successfully.

I believe OCR was the use case, but I'm treating that as provisional because nothing I have names the specific application or model. The OCR worker later in this article is a realistic example, not our production workload or a benchmark.

The three controls do different jobs

The node label describes where something can run. A pod's node selector or required affinity uses that label to pick the pool. The taint keeps pods away unless they carry a matching toleration. The extended resource request tells the scheduler how many GPU devices the container needs.

A toleration allows a pod onto a tainted node. It doesn't pull the pod there and it doesn't allocate a GPU. A selector narrows placement but doesn't allocate a device either. The integer nvidia.com/gpu request is what makes device capacity part of scheduling.

Our taint value was the string True, capital T included. An Equal toleration needs that exact value and effect. An Exists toleration can match the key without a value, but widening a toleration should be a deliberate choice. NoSchedule stops new pods without a match; it doesn't evict pods that are already running. Kubernetes taint and toleration behavior.

A small GPU setting needs an end-to-end contract

What the configuration proves, and what the rendered workload still has to show.

Request acceleration

The parser supports boolean or integer GPU input with a zero-to-two range. The business workload may have been OCR; that recollection remains provisional.

gpu: true -> 1
gpu: false -> 0
integer: 0..2

What the application interface supported

The application manifest parser added a GPU setting with a range from zero to two. gpu: true meant one GPU, gpu: false meant zero, and you could also give an integer in range. Anything else was rejected. The parsed value became an integer in the service's container resource configuration.

That's a nice developer-facing interface. Someone who needs accelerated capacity shouldn't have to learn the cluster's whole node setup. The platform can offer a small supported contract and translate it into the Kubernetes details.

There's an important gap, though. The values template I looked at rendered CPU and memory, but not the GPU field. The Deployment template could take resource values and tolerations, but that alone doesn't prove gpu: true ever turned into a GPU request.

I'd check the rendered output before calling this an end-to-end feature. A parser test isn't enough. The check that matters is that the GPU setting produces an extended resource request and limit, the right placement controls, and an image that can actually use the device.

An illustrative OCR worker

Picture a worker that picks up a document task, prepares the images, runs an OCR model, and stores the result. Some OCR engines run fine on CPU. Others use accelerated inference. Before making GPU the default path, we'd want evidence that the chosen model actually benefits from one.

For the accelerated version, the contract is one GPU per worker process, bounded concurrency, and jobs that are safe to retry. A duplicate delivery shouldn't create duplicate results. Model loading and warm-up also belong in the worker's readiness and scaling design.

Below is a generalized pod spec fragment. It isn't the original manifest or a complete runnable workload. It shows the scheduling contract the deployment generator needs to produce for a one-GPU Auto Mode worker:

yaml
spec:
  nodeSelector:
    eks.amazonaws.com/compute-type: auto
    gpu-type: nvidia
  tolerations:
    - key: nvidia.com/gpu
      operator: Equal
      value: "True"
      effect: NoSchedule
  containers:
    - name: ocr-worker
      image: registry.example.com/ocr-worker:example
      resources:
        requests:
          cpu: "2"
          memory: 4Gi
          nvidia.com/gpu: 1
        limits:
          cpu: "4"
          memory: 8Gi
          nvidia.com/gpu: 1

The CPU and memory numbers are placeholders, not sizing advice for an unknown OCR model. The GPU quantity is an integer, and the request and limit are equal. Kubernetes also lets you set only a GPU limit, in which case the request follows it. Kubernetes GPU resources.

Devices need to be exposed to Kubernetes

A GPU instance type doesn't guarantee that nvidia.com/gpu shows up in the node's allocatable resources. The drivers and device integration have to be healthy, and the container has to be compatible with the environment.

Our earlier self-managed Karpenter setup offered GPU-capable images, including an NVIDIA-oriented Bottlerocket variant and an older EKS GPU image path. Those were choices for their time. I'd check current image support and the driver and device-plugin lifecycle before reusing any of it.

EKS Auto Mode's accelerated path manages the NVIDIA driver and device plugin on supported nodes. The workload still needs the right placement and device resources. Auto Mode changes what the platform has to install, but you still have to check image compatibility, node allocatable state, and the application itself. Auto Mode accelerated workloads.

For a first deployment: confirm the node is Ready, check the expected device count, inspect the pod's rendered request, and run a controlled application check. Getting scheduled is only one step. The model can still fail to load, or quietly run on CPU because of a configuration mistake.

The interactive example looks at one dedicated node with two allocatable GPUs, one already in use. It checks a small slice of scheduling: the taint match, the device integration, the requested quantity, and whether the node meets the other modeled requirements. It doesn't simulate every scheduler plugin or predict whether the cloud will have the node available.

A worker asking for two GPUs won't fit on the one that's left. A missing toleration blocks scheduling onto the tainted node. A pod with a toleration and no GPU request may be allowed onto the node without getting a GPU, which is a good reason to validate the application contract at admission.

Without the explicit pool selector, a GPU request still needs GPU-backed capacity, but it no longer says it prefers our dedicated pool. That matters once there's more than one accelerated pool.

Scheduling policy is not an authorization boundary

Taints control placement, not access. Anyone who can create arbitrary pod specs can add a toleration. A real platform boundary needs RBAC, namespace or team limits, and admission policy deciding who can request accelerated resources and which placement controls they can use.

I'd require an application owner and cost allocation metadata on every GPU request. Define a supported range, reject anything outside it, and cap each team's consumption with a quota or another reviewed policy. Keep a clear exception path for workloads that really need a different device shape.

The parser's zero-to-two range is an application interface limit. It doesn't mean a cluster-wide quota or admission policy enforced the same range. Those checks are how I'd finish the platform contract, not something I'm claiming already existed.

Monitor useful work as well as allocated devices

Allocating a device and using it are different things. An allocated GPU can sit idle while the process waits on a document download, the database, image preparation, or a full downstream queue. Node allocatable and pod resource data tell you about scheduling inventory. Utilization and GPU memory need proper device telemetry.

I'd build a Grafana view around pending GPU pods, allocated versus allocatable devices, job queue age, processing time, failed and retried jobs, model initialization time, and application throughput, plus utilization and GPU memory where device telemetry exists. I can't say a DCGM exporter or these exact panels were installed; this is the monitoring I'd set up.

For an OCR worker, accuracy and output quality matter as much as speed. A faster worker that produces worse text isn't an improvement. Test with representative documents, model versions, CPU and GPU paths, batch sizes, and concurrency, and use the results to choose capacity and justify acceleration.

Cost and lifecycle decisions

The GPU pool used on-demand capacity, so I wouldn't describe it as a Spot strategy. GPU capacity can be scarce, and a retryable job design is only one part of deciding whether interruptible capacity is acceptable.

Scale from application demand and recovery requirements. A queue-driven worker might justify KEDA, but its maximum replicas have to respect available devices, model startup time, downstream capacity, and budget. If the model loads slowly, aggressive scale-to-zero can hurt processing latency.

When the queue drains, make sure finished workers release their requests and node consolidation can safely reclaim the capacity. Give GPU cost its own view in the allocation model, because generic CPU and memory coefficients can understate what accelerated infrastructure really costs.

The lesson is the whole chain: a small developer request, a correctly rendered manifest, restricted and suitable capacity, healthy device exposure, observable application work, and an accountable cost owner. We had important parts of that chain in place. Being upfront about what still needs validating is what makes the story credible.
