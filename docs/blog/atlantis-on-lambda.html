Running Atlantis on Lambda: lifecycle, performance, and recovery

What it took to fit a long-running Terraform automation service into an invocation-based runtime: the webhook race, warm-process reuse, deadline reporting, and container-image checks.

Atlantis is normally a long-running service. It receives repository events, checks out code, plans infrastructure, and reports back to the pull request. It can sit idle for long stretches, but when it's busy, the work can take minutes and can change real infrastructure.

That made Lambda an interesting place to explore the cost tradeoff. Paying for active execution instead of an always-on worker is attractive for a workflow with quiet periods. The real question was whether the service's lifecycle could fit the runtime without losing work or leaving engineers unsure what happened.

This article covers my work on the Go wrapper and build workflow in the Atlantis-on-Lambda repository, including changes from September 2026. It's separate from the earlier Kubernetes-based Atlantis work at CLARK. An earlier Lambda attempt had already flagged asynchronous processing as a blocker. The later implementation fixed parts of that problem, but I wouldn't say it solved every durability or execution-limit concern.

The architecture we were adapting

The wrapper used the Lambda Go runtime and accepted API Gateway V2 HTTP events. It started an Atlantis process inside the execution environment, waited for its health endpoint, and forwarded requests to the local service.

text
GitHub webhook or Atlantis UI/API request
                    |
                    v
HTTP entry point -> Lambda Go handler
                    |
              ensureAtlantis()
                    |
                    v
          local Atlantis process :4141
                    |
       Terragrunt -> Terraform -> cloud APIs
                    |
           plan output / PR comments

For GitHub webhooks, the handler normalized the target path to /events. For UI and API requests, it kept the original path and query string. That mattered for job pages and other Atlantis endpoints; a proxy that treated every request as a webhook would break the service's normal interface.

It also handled base64-encoded request bodies, response content types, binary responses, and cookies, and stripped forwarding headers that didn't belong. None of that is as dramatic as the Terraform operation, but it's what makes an HTTP adapter behave like the service it wraps.

Warm-process reuse without assuming permanent availability

Starting Atlantis on every invocation would repeat process startup, secret loading, and readiness checks each time. The wrapper kept the subprocess in package-level state and guarded startup with a mutex. When Lambda reused an execution environment, the existing process could be reused after a health check. If the process had exited, the wrapper cleared its recorded state so a later invocation could start a fresh one.

The Atlantis process ran under a process-level context, not the current request's context. That let it survive an ordinary finished UI request inside a reused environment. The handler still had to keep real webhook work inside a suitable invocation lifetime.

Warm reuse is an optimization, not durability. Lambda can freeze or replace an execution environment at any time. A local process and a local cache can't be the only record that an infrastructure operation exists. AWS documents the execution-environment lifecycle.

The Atlantis data directory defaulted to /mnt/atlantis, and the locking database defaulted to Redis. The code names those dependencies, but a directory name doesn't tell you how storage was provisioned in a particular deployment. Durable files, Redis availability, permissions, networking, and concurrency all still depend on the infrastructure around it.

The race that could silently drop a plan

The key bug was easy to miss because the HTTP request looked successful.

Atlantis acknowledged /events before its asynchronous command processing had necessarily started. So an immediate check of /status could report zero in-progress operations. That zero could mean "this event needs no work" or "the work hasn't started yet."

If the Lambda handler returned at that point, the runtime could freeze while Atlantis still had work waiting to start. The pull request would never get a plan comment, even though the webhook had reached the process.

Why an HTTP success could still lose the plan

Compare an immediate return with the two-phase wait added to the wrapper.

Receive the event

The wrapper ensures a healthy local Atlantis process and forwards the webhook to /events.

GitHub event -> local /events

The fix was a two-phase wait. First, wait briefly for activity to appear. Then, once you've seen it, wait for it to finish.

go
// Reconstructed algorithm, simplified from the wrapper.
for withinStartGracePeriod() {
    status := readAtlantisStatus()
    if status.InProgressOperations > 0 {
        observedWork = true
        break
    }
    waitShortInterval()
}

if observedWork {
    for withinInvocationBudget() {
        if readAtlantisStatus().InProgressOperations == 0 {
            return nil
        }
        waitCompletionInterval()
    }
    return deadlineExceeded
}

return nil // event treated as starting no work within the grace period

The defaults were a ten-second start grace, a 100-millisecond poll during that phase, and a 500-millisecond completion interval. Where it made sense they were configurable, so an operator could tune behavior without a rebuild.

This fixed the immediate-zero race. It didn't add durable per-event completion tracking. The status counter was global to the process, and in principle work could start and finish between polls. Slow scheduling past the grace period was another gray area. I'd call this a targeted lifecycle fix, not a queue with exactly-once processing.

Reserve time to explain a timeout

A long Terraform operation could use up the entire standard Lambda invocation limit. If the runtime killed it with no time left, the engineer would see a silent pull request and have to piece the outcome together from logs.

So the wrapper worked out its waiting budget from the invocation deadline and held back a configurable reserve, sixty seconds by default. A separately configured maximum wait could shorten that budget further.

text
remaining invocation time
          - deadline reserve
          = time available to wait for Atlantis

if an explicit maximum wait is shorter:
    use that shorter budget

On timeout, the handler identified the pull request from the webhook, tried to list matching Atlantis locks, optionally released project locks, and used a GitHub App client to post an explanation. It matched on repository identity and pull-request number, so it couldn't confuse two repositories that happened to share a PR number.

Commenting was best effort. If listing or releasing locks failed, it logged the error and carried on to the notification. Cleanup shared a bounded time budget, so a slow lock API could still eat into the time left for the comment.

The operational distinction is crucial: these were Atlantis project locks, not Terraform backend state locks. Releasing a coordination lock didn't mean Terraform had stopped, finished, or rolled back. The wrapper's report also didn't kill the subprocess before returning, so an operation could still be running when recovery started.

That's why I'd think hard before enabling automatic lock release on a live apply path. Recovery has to establish whether a writer is still running, check the actual state of the cloud resources, and produce a fresh plan. A timeout message is useful feedback. It isn't a transaction rollback. Terraform's state-locking documentation explains the separate backend mechanism.

The ingress deadline was a different limit

Raising the Lambda timeout didn't make the whole HTTP path suitable for a long Terraform apply. Standard Lambda functions max out at a 900-second timeout. API Gateway HTTP APIs have a maximum integration timeout of thirty seconds. GitHub expects webhook responses within ten seconds. Those are three different clocks. AWS documents the Lambda timeout, the HTTP API quota, and GitHub documents webhook response expectations.

The wrapper waited for work inside the handler before returning its proxied response. So a quick local acknowledgement from Atlantis didn't necessarily mean a timely acknowledgement to GitHub across the full request path.

A stronger design would separate accepting an event from executing it:

Separate acceptance from execution

This is a proposed stronger event path, not a claim that a durable queue already exists in the wrapper.

Validate delivery

Verify the signature and identify the delivery. Do not wait for a full infrastructure operation before acknowledging acceptance.

delivery ID + signature + repository

A fast ingress would validate the webhook signature and persist the event before acknowledging it. The worker would then need delivery IDs, retry handling, deduplication, and a clear command status. A queue on its own wouldn't extend a Lambda worker's execution limit; long applies might need a container worker or a different execution model altogether.

I'd also handle failed deliveries on purpose rather than assume GitHub retries every unsuccessful request. Durable acceptance and redelivery need to be designed and tested.

Removing work that did not improve the result

The Terragrunt workflow had several concrete performance wins.

First, I removed --source-update from the plan path. That flag threw away and re-fetched module sources even for repeated plans of the same pinned reference. With sources pinned and the cache keyed by source and revision, changing a reference already selects a new source. Re-fetching unchanged modules on every plan was wasted work.

Second, I removed the unconditional terragrunt show -json from a workflow that didn't have policy checks enabled. Plan JSON is useful when a policy engine reads it. Without one, generating it just added time without changing anything the engineer needed. If policy checks come back, JSON generation should come back in that stage.

In one observed plan, the JSON conversion took roughly thirty seconds of a 145-second single-project run. That's a diagnostic observation, not a general benchmark or a promise that every plan speeds up by the same amount.

Third, Git's safe-directory configuration moved out of a per-event pre-workflow hook and into the image build. That stopped a configuration command from running, and appending duplicate entries, on every webhook. The broad trust setting in the image still deserves its own explicit security decision; moving it earlier made it cheaper, not narrower.

The workflow also set Terraform parallelism and lock-wait behavior. Both affect latency, but more parallelism isn't automatically better. Cloud API throttling, memory pressure, and dependent state reads can all change the outcome.

Building an image Lambda could actually run

The build workflow replaced a manual build, push, and redeploy loop with a repeatable pipeline. It ran Go formatting checks, go vet, race-enabled tests, and a Linux build. Pull requests built and scanned without publishing. The publishing path assumed an AWS role through GitHub OIDC, pushed to ECR, and reported the image digest for the infrastructure config to pin.

text
Go checks -> container build -> scan -> publish when authorized by workflow
                                                    |
                                           inspect image manifest
                                                    |
                                           report immutable digest
                                                    |
                               infrastructure PR pins digest -> plan -> apply

One especially useful guard checked the pushed image manifest. Container builds can publish an OCI index that holds an image plus attestation manifests, but Lambda needs a single compatible image manifest, not the index.

So the workflow built for a single target architecture, turned off inline provenance and SBOM attestations for this image, and verified the pushed artifact wasn't an image index or Docker manifest list. AWS documents Lambda container-image requirements.

That was an artifact-compatibility check, not a statement that provenance and SBOMs are bad in general. A stronger supply-chain setup could store attestations separately while keeping the runtime image compatible.

The Trivy scan in this workflow reported high and critical findings with an exit code of zero. In other words, it was informational, not a blocking security gate. That's worth saying plainly so nobody over-reads what a green build meant.

Secrets, persistent files, and concurrency

The wrapper fetched the GitHub App key, the webhook secret, and an optional Redis password from Secrets Manager by name. It cached the values inside the execution environment and wrote the App key to a file for the local Atlantis process.

That kept literal credentials out of the repository and out of container build arguments. It also created an operational requirement: cached values and warm processes need a rotation plan. A changed secret may need a fresh execution environment or a deliberate cache refresh.

Persistent Atlantis files and distributed coordination needed explicit handling too. Redis coordinated Atlantis locking; Terraform state stayed in its configured backend. Plan artifacts, checkouts, provider caches, and command logs each had their own persistence and access needs.

A process-local mutex prevents duplicate startup within one process. It does nothing across multiple Lambda execution environments. As concurrency grows, shared storage paths, project locks, backend writes, and worker ownership all have to stay safe across instances. That's where the surrounding infrastructure and the operating model matter as much as the Go handler.

Monitoring the whole operation

What you need to monitor is bigger than Lambda's invocation metrics. A delivered webhook, a started Atlantis operation, a finished Terraform command, and a posted pull-request result are four separate milestones.

I'd record a delivery ID and correlate it with the repository, pull request, project, and invocation. Prometheus or any other metrics system should use bounded dimensions for aggregate counters; individual deliveries and full payloads belong in logs or traces, not in unbounded metric labels.

SignalWhat it tells the operator
Accepted events versus completed resultsWhether work is disappearing between ingress and execution
Cold-start and readiness durationWhether startup is consuming a meaningful part of the budget
Operation duration and reserved-budget exitsWhether the runtime fits the workload
Errors contacting secrets, Redis, storage, or cloud APIsWhich dependency is blocking execution
Failed PR notificationsWhether engineers are missing the result even when processing ran
Redeliveries and duplicate commandsWhether recovery risks repeating an operation

With a short-lived runtime, a traditional periodic scrape of an in-process endpoint can miss most of the activity. I'd pick an export path that suits the worker's lifetime and combine runtime logs with cloud metrics. A Grafana view should show the full delivery journey and link to the logs you'd need for recovery.

This monitoring plan is a proposal. I'm not claiming every metric and dashboard listed here was already deployed.

A rollout plan that tests the real constraints

I'd validate this architecture in stages instead of treating a successful image build as the finish line.

  1. Test the adapter. Check ordinary UI paths, query strings, cookies, binary responses, malformed bodies, process startup, and process restart behavior.
  2. Reproduce the asynchronous race. Verify that an acknowledgement before work starts does not cause an immediate return. Test no-work events, late starts, and status failures as well as the normal path.
  3. Test through the actual ingress. Compare webhook delivery time with operation completion time, and confirm how failed or duplicate deliveries are handled.
  4. Exercise a controlled long operation. Validate the reserved deadline, notification behavior, remaining writer status, project locks, and the subsequent fresh plan.
  5. Validate shared dependencies and concurrency. Test persistent data, secret rotation, Redis loss, and simultaneous requests against the intended deployment settings.
  6. Compare full operating cost. Include invocation duration, storage, Redis, networking, logs, cold starts, and engineering recovery time alongside the idle compute removed.

The biggest lesson from this work: the runtime's lifecycle has to match the service's lifecycle. These changes fixed specific failure modes and cut avoidable overhead. The open architectural questions, especially durable acceptance and long-running execution, decide whether it's dependable enough to become the default path for infrastructure changes.
