From Cluster Autoscaler to Karpenter and EKS Auto Mode

What made this journey interesting was how our control over capacity changed: first scaling predefined node groups, then picking nodes for pending workloads, then handing more of the node lifecycle to a managed service.

Start with the problem each stage solved

Our Kubernetes clusters ran applications, CI workloads, and dynamic testing environments. They didn't have the same resource shape or lifetime. A burst of build jobs needed capacity fast, an application needed predictable placement and safe disruption, and a testing environment might be gone by the end of the day.

Cluster Autoscaler was a familiar place to start. Our Deployment discovered Auto Scaling Groups through Kubernetes cluster tags, and its configuration included a scale-down utilization threshold, an AWS service account integration, health checks, and metrics. It grew or shrank groups whose instance configuration we'd already chosen.

That model was easy to understand, but it left us maintaining the menu of node groups. If none of the groups fit a workload, adding more of the same node didn't necessarily use capacity well. We had to think about how many nodes we needed and what shape they should be.

We documented the move toward workload-driven provisioning in a Karpenter guide. Later, the infrastructure code gained EKS Auto Mode configuration and a migration guide, which was openly marked as a work in progress. I can walk through the progression and the configuration, but I can't claim every production workload completed the final migration.

What changed with Karpenter

Karpenter put the pending pod's requirements at the center of the capacity decision. Instead of always growing a predefined group, it could pick a compatible instance from whatever a NodePool and its AWS node configuration allowed.

That flexibility still needed boundaries. Our templates set architecture, operating system, availability zones, capacity type, and instance constraints. NodePool limits capped total provisioning. There were consolidation and disruption settings too. All of these were operating policies we had to review against our workloads, not defaults to accept blindly.

Resource requests mattered a lot more. Both the scheduler and the provisioner work from declared demand. An application that reserves far more memory than it uses pushes you toward bigger nodes and makes consolidation harder. One that requests too little looks efficient right up until it struggles under load. Rightsizing needs real measurements and a workload owner, not one universal request-to-limit ratio.

For developers, the goal was simple: a DTE or a build should get suitable capacity without filing a ticket for a new node group. For the platform team, the work shifted toward explaining constraints and figuring out why a pod couldn't be placed.

Consolidation needs a service contract

Our Karpenter template allowed consolidation of empty or underused nodes after a configured delay, and supported disruption budgets and termination grace periods. Those settings have to work with how applications shut down, their disruption allowances, storage constraints, and service objectives.

A node that looks underused isn't necessarily safe to remove right away. Think of a worker in the middle of a long job, an application with a single replica, or a volume that can only attach in one availability zone. Removing capacity without understanding those constraints trades a lower infrastructure estimate for a broken service.

I'd review disruption as a sequence: pick a candidate, check that replacement capacity is possible, understand which pods will move, allow graceful termination, and watch the application recover. The longest acceptable recovery time belongs in the service's operating requirements.

Old templates need schema checks before anyone reuses them. One of our self-managed NodePool templates put expiry under a disruption block, and a custom-requirements loop still had literal placeholder values. I'd validate and render templates like that against the target Karpenter version before calling them deployable. The later Auto Mode template had a different shape altogether. Copying an old guide without that review hides a real part of the migration work.

Measure application readiness, not only node speed

An earlier experiment compared Bottlerocket with a custom Amazon Linux 2 image, using the same instance type and a large container image. The observed node-assignment segment took about 38 seconds versus 47. First image pulls took about 54 seconds versus 42 in the respective traces. A later run benefited from an image that was already cached.

Those are useful observations from a small experiment, not general performance promises or a statistical benchmark. They also show why a faster node-assignment step doesn't automatically mean a faster ready application.

I'd measure the whole path: demand appears, the pod goes pending, a node is requested, the node registers and becomes Ready, the image is available, the container starts, and the application passes readiness. DNS, network access, credentials, image size, initialization, and database migrations can easily dominate that last stretch.

The Amazon Linux 2 comparison belongs to its time. Choosing an image today means checking current EKS and image support, security maintenance, and compatibility. The lesson that still holds: measure what users see, and don't pick an image from a single timing.

What EKS Auto Mode changed

The later infrastructure code turned on Auto Mode for a development cluster and defined general-purpose and NVIDIA GPU pools. It also set up managed node roles, an EKS-specific NodeClass, node placement configuration, and storage classes for the Auto Mode EBS driver.

Auto Mode runs on Karpenter technology, with AWS taking on more of the compute, networking, and storage lifecycle. That changes which components we install and maintain. It doesn't take away responsibility for workload requests, placement policy, disruption tolerance, permissions, or application health. EKS Auto Mode responsibilities.

The cost decision also has to include the managed-service charge, the underlying compute, and how operational effort changes. A node-hour dashboard alone can't tell you whether the move was worth it. I'd compare the same workload demand and reliability requirements before drawing any cost conclusion.

Reworking the old migration guide

The work-in-progress guide included bulk changes to controllers and add-ons, manual drains, state manipulation, and disruptive storage steps. I wouldn't use it as a production runbook today. A safer approach is a series of reversible workload cohorts, with clear ownership of both the old and the new capacity.

Current AWS guidance supports running self-managed Karpenter and Auto Mode side by side during a migration. It describes moving workloads selectively with placement controls and warns about shared Karpenter resources. That points to a canary approach, not to treating an enabled cluster flag as a finished migration. AWS migration guidance.

Here's how I'd roll it out:

  1. Inventory node owners, workload selectors, taints, controllers, add-ons, volumes, and disruption requirements.
  2. Create a constrained Auto Mode pool and keep existing capacity available.
  3. Move a stateless canary intentionally and test startup, connectivity, logging, scaling, and disruption.
  4. Expand to a small workload cohort, measuring service health and recovery against the previous behavior.
  5. Validate stateful workloads and storage separately, including a tested restore path.
  6. Retire an old component only when no remaining workload depends on it and recovery has been demonstrated.

To place specific workloads on Auto Mode compute, use the eks.amazonaws.com/compute-type: auto selector. A temporary migration taint with a matching toleration keeps unrelated workloads off the canary pool. The rest of the pod's resource and topology requirements still have to match.

Storage deserves its own migration

The old EBS CSI provisioner and the Auto Mode one have different driver identities: ebs.csi.aws.com and ebs.csi.eks.amazonaws.com. Renaming a StorageClass or switching its provisioner doesn't mean an existing volume has moved safely.

I'd record which workload uses each volume, its availability zone, access mode, reclaim policy, snapshot support, and recovery procedure. Keep the original data until a restored or migrated volume has been checked with the application. Keep the old driver and compatible compute around while any volume still depends on them.

AWS offers an EBS migration tool built on volume snapshots, and documents what to watch for with mixed compute placement. It's a starting point for a plan per workload, not permission to delete a production PVC and assume the replacement holds the same data. AWS EBS migration tool.

Observability has to survive the move

Our Karpenter Grafana dashboard estimated node cost by joining node instance-type labels to a Karpenter offering-price metric. That's a genuinely useful detail, and it also creates a migration dependency: the dashboard needs a review if its price source or labels disappear under the managed model.

I'd keep pending-pod age, node readiness, provisioning failures, disruption events, image-pull time, and application readiness in the operational view, with node-hours and a clearly labeled cost estimate next to them. Missing price data should show up as an allocation exception, not quietly become zero cost.

Our all-cluster cost query grouped by instance type while mixing price estimates across clusters. A current version should keep region and other pricing dimensions before picking a rate, because the same instance type can cost different amounts in different places. An offering estimate also needs reconciling with billing, since it doesn't include every commitment, credit, or fee.

The bigger lesson: fewer components to maintain is worth a lot, but the platform contract still has to be explicit. Developers need suitable capacity and useful feedback. Operators need a clear owner for every node, a safe disruption path, and monitoring that keeps explaining the system after the implementation underneath it changes.
