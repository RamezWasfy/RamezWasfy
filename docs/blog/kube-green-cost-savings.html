Giving non-production workloads working hours with kube-green

A test environment can be useful all week without running all night. I used kube-green to make that difference explicit, and kept the controllers and checks we needed to bring things back safely in the morning.

Why another cost control was needed

Our testing platform made it easy to run an application somewhere other than a developer's laptop. A feature could get its own environment, and the team could open a URL during a sprint demo. The downside of that convenience was obvious after a while: plenty of workloads kept running overnight with nobody using them.

Deleting an environment and pausing it solve different problems. Our ephemeral DTEs already had a scheduled cleanup path. Persistent testing environments were different, because someone might need them tomorrow with the same configuration and data. Asking every developer to remember a manual shutdown was never going to work. A working-hours policy put the expected lifetime in configuration, where everyone could see it.

I treated it as a platform feature, not a cost script. A developer should know when their environment is available, how to ask for an exception, and what to do if it doesn't wake up. The infrastructure team should know which resources the schedule controls and which costs keep running.

What the implementation actually controlled

A Terraform module deployed the kube-green controller and created a SleepInfo resource for each configured namespace. Shared defaults set weekday sleep and wake times, and a namespace could override them for a team that kept different hours.

We ran an older controller version, with permissions for Deployments, CronJobs, and the controller's own custom resources and saved state. Our SleepInfo template suspended Deployments and CronJobs. So I wouldn't say that setup covered every Kubernetes workload type. Newer kube-green releases do more, including StatefulSets, but turning that on means checking the controller version, resource configuration, permissions, and how each application recovers. Current kube-green configuration.

Here's the shape of our schedule, with a made-up namespace. Note the explicit autoscaler exclusion:

yaml
apiVersion: kube-green.com/v1alpha1
kind: SleepInfo
metadata:
  name: working-hours
  namespace: preview-team
spec:
  weekdays: "1-5"
  sleepAt: "20:00"
  wakeUpAt: "08:00"
  timeZone: Europe/Berlin
  suspendDeployments: true
  suspendCronJobs: true
  excludeRef:
    - apiVersion: apps/v1
      kind: Deployment
      name: aws-cluster-autoscaler

The exclusion only matters where that Deployment lives in the selected namespace. Its job is to keep the capacity controller running while the application workloads sleep. The kube-green controller itself also needs to live somewhere the policy can't suspend it by accident.

In practice, not every team used the defaults. One staging environment slept at 22:00 and woke at 06:00. A development environment changed only the wake time. Because the overrides lived in the infrastructure repository, they went through the same plan and approval workflow as any other platform change.

Sleeping is a state transition

At sleep time, a Deployment goes from its current replica count to zero. At wake time, that previous count has to be available so it can be restored. kube-green stores the pre-sleep state in a Secret tied to the SleepInfo, and CronJob suspension is restored the same way. That saved state is part of the operating contract. It isn't throwaway configuration. Sleep and wake lifecycle.

Suspending a CronJob stops future runs. It doesn't mean a job that's already running has finished, or that its side effects have stopped. A nightly import, for example, needs a deliberate decision: let it finish, cancel it, or exclude it.

Weekday schedules are easy to misread too. With Monday to Friday, Friday's sleep state can last until Monday's wake event, as long as no other controller or person changes replicas over the weekend. It isn't a separate rule that keeps forcing every weekend workload to zero.

Time zones need the same care. Europe/Berlin follows daylight saving. A local schedule is friendlier for people, but the wake-up alert and the cost comparison have to read time the same way. And a calculation for a normal week is no substitute for watching the real transitions.

Why zero replicas does not mean a zero bill

kube-green changes workload state. It doesn't terminate EC2 instances, delete namespaces, remove EBS volumes, or cancel reservations. Getting lower compute spend depends on a second control loop: the node autoscaler has to notice the spare capacity and be allowed to remove it.

There are good reasons a node might stay. A minimum system pool still runs core services. Another workload might share the node. Disruption rules, placement constraints, or safety requirements can block consolidation. Load balancers, retained storage, and other services keep costing money after the replicas stop.

So I'd present the saving as reducible capacity-hours first, then check it against the actual bill. With five twelve-hour working days, an application is meant to be awake for 60 of 168 hours. The other 108 hours are a possible reduction in its variable footprint. They don't prove a 64% cut in the whole environment bill.

Avoiding fights between controllers

A Deployment rarely has just one writer. An HPA, a KEDA-generated HPA, a GitOps reconciler, and a person changing replicas by hand can all interact with a sleep policy. Before enrolling a workload, I'd check how those specific versions and settings behave together.

Three questions come first. Ownership: which controller is allowed to set replicas during sleeping hours? Recovery: what brings back demand-driven scaling after the wake event? Visibility: can an engineer tell an intentionally sleeping app from a broken one?

Some of our environments had KEDA-related namespaces in the sleep configuration, which makes controller placement especially important. Pausing a scaling component can be fine in a contained non-production environment. It shouldn't quietly take out the controller that unrelated workloads need to recover.

I'd start a rollout with one stateless preview service. Watch its normal replica count, the sleep transition, the saved state, and how it comes back in the morning. Then add the dependencies that can live with the same schedule. Databases and shared services get their own decisions. A schedule isn't a recovery test.

What I would monitor in Grafana

Our Grafana dashboards already split out resource requests, estimated cost, and workload health. I'd extend that with a schedule view and a recovery view. The illustration above shows the structure I have in mind. It's a teaching reconstruction with sample data, not one of our real dashboards.

The schedule view should show which namespaces are enrolled, their time zone and override, their owner, and their current intended state. Next to that, show desired and ready replicas. A sleeping service with zero ready replicas is expected. An awake service with zero ready replicas needs someone to look at it.

The recovery view should track time from the wake event to readiness, pending pods, node provisioning delays, and dependency failures. Controller reconciliation errors and missing saved state each need their own attention. A workload can get its replica count back and still fail its readiness checks.

For cost, compare node-hours and the eligible compute spend before and after enrollment, then reconcile with billing data. Keep storage and shared infrastructure visible. If workloads are sleeping fine and the bill hasn't moved, look at allocation boundaries or consolidation before assuming the sleep events are broken.

A practical rollout and exception process

I'd make each namespace enrollment a small infrastructure change with an owner and a written availability window. Before merging, review the exclusion list, scheduled jobs, dependencies, and who owns replicas. Run at least one full sleep-and-wake cycle before widening the scope.

Exceptions should have a reason and an expiry. A late sprint demo is a perfectly good reason to keep an environment awake. A permanent override nobody can explain usually means the default schedule or the workflow needs fixing. The owner should find the exception in the same place as the normal policy.

Write recovery steps in application terms: restore the intended workload state, check dependencies, confirm readiness, and open the environment URL. Restoring replicas on its own isn't enough. Neither is deleting the SleepInfo without understanding the saved state and the current replica count.

This work sits next to the DTE lifecycle and node autoscaling. Cleanup removes environments that have outlived their use. Scheduled sleep keeps environments around between uses. Node management turns lower workload demand into a possible reduction in actual capacity. Keeping those three ideas separate made our cost conversations much more useful.
