Versioned Terraform modules and checks before review

How a separate module repository gave consumers an explicit choice about when to upgrade, and how pre-commit turned formatting, validation, docs, and security checks into a routine.

At CLARK, our infrastructure workflow kept reusable Terraform modules and stacks in their own repository. The infrastructure repository pointed at released module references; the module repository held the implementation and its docs. I worked on the Terraform and Terragrunt platform, including the guides and practices that made this split usable day to day.

The point of separating them wasn't tidier directories. A shared module can affect many environments at once. We needed a way to improve a pattern without every consumer silently picking up the change, and a way for reviewers to see an upgrade as a deliberate infrastructure change.

The second part was feedback. Review should be about resource behavior, permissions, compatibility, and operational impact. Nobody should need a teammate to point out every formatting slip, missing variable description, or stale generated input table. Local checks could catch a good chunk of that earlier.

The problem with shared code without a release contract

Pulling a module from a moving branch makes the source look stable while its behavior shifts underneath the consumer. Replanning an environment nobody touched can suddenly show a different result after a module update. That makes it hard to say which implementation a given environment is actually running.

Copying modules into every environment causes the opposite problem. Consumers are independent, but every fix has to be repeated, the copies drift apart, and nobody can easily tell which one is the intended pattern.

We kept one central implementation and made consumers pick a reference. That gave us reuse and a reviewable upgrade boundary.

A release was only part of the contract. We also had to explain what changed, which consumers were affected, and what their plan should look like when they upgraded.

Repository boundaries and module shape

The module repository had provider-specific modules and higher-level stacks. The infrastructure repository supplied the deployment context: account, project, region, environment, and ownership.

A generalized layout:

text
terraform-modules/
  modules/
    aws/
      application/
        main.tf
        variables.tf
        outputs.tf
        versions.tf
        README.md
    gcp/
      dataset/
  stacks/
    platform-service/
  .pre-commit-config.yaml

infrastructure/
  aws/accounts/.../application/terragrunt.hcl
  gcp/projects/.../dataset/terragrunt.hcl

Each leaf unit in the infrastructure repository chose the module version and passed inputs. The module described the resources and the variation it supported. That pushed us to think about defaults and public interfaces instead of exposing every implementation detail as one more variable.

A module still needs a coherent scope. One that tries to cover every networking or application scenario can end up harder to use than the raw resources it wraps. I'd rather have a small, documented pattern with a few intentional escape hatches than a pile of loosely related boolean switches.

Pinning made upgrades visible

A Terragrunt consumer could reference a specific release of the module source. This example uses a generic repository URL:

hcl
terraform {
  source = "git::https://example.com/engineering/terraform-modules.git//modules/aws/application?ref=v2.4.1"
}

inputs = {
  application_name = "payments"
  environment      = "staging"
  replica_count    = 2
}

The double slash selects a subdirectory and ref selects the revision. Bumping the version shows up right in the infrastructure diff:

diff
- ref=v2.4.1
+ ref=v2.5.0

That's easy to read, but the plan is still the source of truth for what happens to resources. A minor-looking bump can still surface a provider behavior change or a new default that matters to an existing consumer.

Tags also rely on discipline. If someone can move a tag, the name alone isn't immutable. Protecting releases, and using a commit reference where it makes sense, makes the contract stronger.

Our release reference covered the whole repository, so several modules were versioned together. That kept distribution simple, but it meant someone using one module needed good release notes to tell which changes affected them. Versioning each module separately is another option, with its own tooling and maintenance cost.

What semantic versioning needed to mean

Semantic versioning only helps once you've defined what your public contract is. The specification defines major, minor, and patch compatibility expectations. For infrastructure modules, I'd count required inputs, outputs, resource addresses, supported provider versions, and operational defaults as part of that contract.

ChangeCompatibility questionTypical release decision
Fix documentation or preserve existing behavior while correcting a bugWill existing consumers still plan as expected?Patch, after verification
Add an optional capability with an unchanged defaultCan existing inputs continue to work without resource changes?Minor, if compatible
Rename a required input or remove an outputDoes the consumer need to change configuration?Major
Restructure resource addressesWill Terraform treat existing resources as new objects without a migration?Major or an explicit compatible migration
Change a security or availability defaultDoes upgrading alter the deployed behavior?A deliberate decision documented in the release notes

That table is how I think about it, not a description of what our release automation did on its own.

What our workflow actually did: when a pull request merged, it checked out the main module branch, worked out the next tag mechanically from the latest one, and created or refreshed a draft release with generated notes. It automated release preparation. It did not look at the Terraform change and decide whether it was breaking, a feature, or a fix.

That gap matters. Bumping a number automatically isn't the same as enforcing compatibility. An engineer still had to review the version decision and the migration instructions for consumers.

Write release notes for the person upgrading

A useful module release note answers a few questions. Which module changed? What does an existing consumer need to edit? Will the plan add, modify, replace, or destroy anything? Is there a required intermediate version? Which provider versions were checked?

A reconstructed example:

text
Module: modules/aws/application
Change: adds an optional service annotation input.
Existing consumers: no configuration change required.
Expected plan: no change unless the new input is supplied.
Validation: reviewed against the staging example.
Migration: no resource address changes.

A breaking change needs more. If a resource address moves, a Terraform moved block can keep the link to the existing object, as long as the Terraform version and migration path support it. Review it together with the resulting plan; don't assume a refactor is harmless just because the cloud resource name didn't change.

I also wouldn't call a downgrade a universal rollback. If an apply already changed real infrastructure or the state structure, pointing back at the previous module reference may not undo everything. Recovery needs a fresh plan and a clear picture of what actually completed.

What we ran with pre-commit

The module repository used pre-commit as one repeatable entry point for checks. Engineers could install the hooks for everyday commits and run everything explicitly before opening a pull request.

bash
pre-commit install
pre-commit run --all-files

That's the developer workflow; nothing here runs against real infrastructure. The checks still need their supporting tools at compatible versions. pre-commit documents hook installation and execution.

Our module configuration covered several different concerns:

CheckWhat it contributedWhat it could not prove
Terraform formattingConsistent syntax layoutGood module boundaries or safe cloud behavior
Terraform validationConfiguration validity against initialized providers and modulesThat a real environment can apply successfully
Provider lock generationReviewable provider selections and checksumsThat every provider upgrade is behaviorally compatible
TFLintProvider and Terraform lint findingsEvery runtime or organization-specific risk
Trivy IaC scanningStatic security findings with configured exceptionsComplete security assurance
terraform-docsGenerated inputs, outputs, and defaults in the READMEA clear explanation of purpose or migration
ShellCheckProblems in supporting shell scriptsCorrect behavior against every external system
detect-secrets and private-key checksSuspicious credential material before reviewThat secrets can never enter the repository
Merge-conflict and file checksBasic repository hygieneA correct infrastructure plan
Protected-branch hookA local reminder to use the review pathServer-enforced branch protection

It also initialized TFLint plugins and generated a README table of contents. The live infrastructure repository had a smaller set of hooks: formatting, shell checks, and secret detection. Both repositories had a pre-commit file, but they didn't run the same validation, and I don't want to imply otherwise.

Early feedback changes review quality

When formatting and generated docs are already consistent, reviewers can spend their attention on what the module does. If a new variable shows up without a decent explanation, the author can fix it while the context is still fresh.

Local hooks can be skipped, so a new setup should run the important checks in CI too. That's my recommendation for a stronger workflow; I'm not claiming every local check was enforced in our remote pipeline.

Secret-detection baselines need review as well. A baseline makes intentional examples manageable, but it can also hide a real credential if someone accepts findings without looking. Every exception should say why the value is safe and how to revisit that decision.

Generated documentation and human explanation

The module configuration ran terraform-docs against README.md, creating or updating the generated sections and sorting inputs by whether they were required. That kept the reference right next to the code.

Here's the level of clarity I want from a variable:

hcl
variable "replica_count" {
  description = "Number of application replicas for this environment."
  type        = number
  default     = 2

  validation {
    condition     = var.replica_count >= 1
    error_message = "replica_count must be at least 1."
  }
}

The generated table can show the type and default. The README around it should explain why two replicas is the default, whether the workload can scale to zero, which external dependencies exist, and what changing the value does in practice.

I'd keep a minimal consumer example next to the reference. It should use the supported public inputs and show a realistic deployment, not a complicated internal environment a new engineer can't reproduce.

An implementation plan for safe module upgrades

A good release process checks both the reusable implementation and the things that consume it. This is the plan I'd follow when introducing or tightening the workflow.

  1. Define the contract. List supported inputs, outputs, defaults, provider constraints, and migration expectations. Identify which changes can cause resource replacement.
  2. Add a reproducible example. Validate a minimal consumer and an existing-state upgrade path. A new deployment alone does not exercise upgrade behavior.
  3. Make checks easy to run. Pin hook versions, document prerequisites, generate reference docs, and keep exceptions reviewable. Repeat the important checks in CI.
  4. Prepare the release deliberately. Review the diff, choose the compatibility level, describe affected modules, and protect the released reference from movement.
  5. Upgrade a non-production consumer first. Change only the module reference where possible, inspect the plan, apply through the normal workflow, and observe the service.
  6. Promote with evidence. Update production consumers after the upgrade behavior is understood, keeping a record of plans and any migration steps.

For high-impact modules, I'd also test upgrading from the oldest supported version and check that moved addresses, imports, and new defaults behave as documented. How deep the testing goes should follow the module's risk, not stamp the same scaffolding onto every trivial change.

What the design achieved

The separate module repository made reuse explicit. Version references let each environment take changes on purpose. Pre-commit made the useful checks repeatable and cut avoidable review work. Generated docs kept the interface visible, and the guides explained how to consume and upgrade it.

What I value most is how the pieces fit together. A module release without a consumer workflow still leaves upgrades painful. Local checks without a real review still leave behavior uncertain. Release references, early feedback, Atlantis plans, and migration notes together gave engineers a clearer way to improve infrastructure without losing track of what their environments depended on.
