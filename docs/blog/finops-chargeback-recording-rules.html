Turning Kubernetes resource data into team cost views

We used ownership metadata, recording rules, and Grafana to make infrastructure cost make sense at the application and team level. The hard part was getting the allocation model consistent enough that people would trust it.

Why the cloud bill was not enough

In a shared Kubernetes cluster, the cloud invoice hides who owns what. It tells you what an account spent on instances, disks, and load balancers. It can't tell a product team which application, testing environment, or leftover volume explains its share.

Our FinOps work connected those two views. Kubernetes gave us workload identity and resource demand. Ownership annotations gave us the application, owner, cost center, and department. Recording rules turned the repeated joins into reusable series. Grafana put the results in front of the teams who owned the workloads.

We used these views for team cost attribution and chargeback discussions. I'd describe the Prometheus model as a near-real-time allocation estimate. Real financial chargeback also needs an agreed policy and reconciliation against billed costs. The implementation work was real, but I wouldn't call every panel an audited accounting ledger.

The data path we built

The recording rules were split into stages: Kubernetes metadata, resource demand, cost proxies, and ownership aggregates. The metadata rules deduplicated annotations and attached them to pods, namespaces, applications, and other resources. The cost rules then carried those ownership labels into their results.

The path that matters is: resource identity, stable ownership metadata, allocation rate, aggregate, dashboard. Lose identity in an early aggregation and you can't explain the total later. If ownership is missing, the cost should stay visible as unallocated.

Requests, usage, and billable capacity

The CPU cost proxy multiplied requested cores by a configured hourly coefficient, and the memory proxy did the same for requested GiB. The model filtered workload phases and joined pod annotations. These were allocation estimates from declared demand. They didn't measure CPU work done or exact cloud charges.

That's a reasonable choice for explaining who's holding shared capacity. A workload can use very little CPU and still reserve enough CPU or memory to affect which nodes get picked. Showing usage next to requests helps an owner see that gap and spot a rightsizing opportunity.

It has limits, though. A fixed coefficient may not reflect the current instance mix, Spot prices, reservation benefits, or unused node capacity. It should have a documented effective date and a clear meaning. Calling a series cost_dollar doesn't turn it into an invoice.

We also had a node estimate that joined node shape, availability zone, and capacity type to a Karpenter offering-price estimate. That's another useful angle, but still an estimate. Nodes filtered out by a Ready check still cost money, and the price source has to be revisited when moving to Auto Mode.

A real policy inconsistency worth explaining

The pod-level combined cost used whichever was higher, the CPU or the memory proxy. Some application and namespace paths built on that combined value. The cost-center aggregate, on the other hand, added CPU and memory together, and so did one of the application dashboards.

So the views could disagree even when every query ran fine. With CPU at 8 units per hour and memory at 10, the max-based proxy says 10 and the additive model says 18. Grouping by a different owner doesn't explain that gap; the views are using different allocation policies.

A constant sample rate multiplied by complete hours yields a period estimate, not an invoice. Real history needs integration, gap detection, and consistent treatment of shared and unallocated resources.

I'd pick one documented model for each allocation purpose and apply it consistently through pod, application, namespace, and team totals, with any alternative diagnostic view clearly named. A max-based bottleneck proxy and an additive resource charge can both be useful. They just shouldn't quietly pretend to be the same total.

I think this is an important part of the story. Cost visibility gets more credible when you explain your assumptions and go looking for inconsistencies, instead of presenting a precise-looking dashboard as proof the model is settled.

Ownership joins are part of correctness

The annotation path carried owner and cost-center information into the cost series. With several clusters, the matching identity has to include the cluster (or an equivalent source label), the namespace, and the pod. A pod name on its own isn't globally unique.

Some of our joins matched on less than that, including a phase filter matched on pod alone. I'd tighten those before stretching the model across clusters. Namespace collisions and duplicated metadata can cause wrong matches, missing values, or many-to-many errors.

A group_left join also needs exactly one metadata series per matching identity on the right side. Deduplication has to keep the single intended owner, not hide conflicting owner labels. I'd turn conflicting ownership into an exception with a visible count and someone accountable for it.

Here's a generalized recording-rule example for requested CPU by team. It's not a copy of our production rules or a full billing model. It assumes a stable cluster label and that kube-state-metrics exports the team label. Check that metadata is unique before using it:

yaml
groups:
  - name: allocation-example
    interval: 1m
    rules:
      - record: pod:allocation_metadata:info
        expr: |
          max by (cluster, namespace, pod, team) (
            label_replace(
              kube_pod_labels{label_team!=""},
              "team", "$1", "label_team", "(.+)"
            )
          )
      - record: team:requested_cpu_cores:sum
        expr: |
          sum by (cluster, team) (
            kube_pod_container_resource_requests{
              resource="cpu", unit="core"
            }
            * on (cluster, namespace, pod) group_left(team)
              pod:allocation_metadata:info
          )

The example deliberately leaves unmatched workloads out of the team series. A complete allocation system has to count those separately in an unallocated bucket. Otherwise a missing label looks like a cost reduction.

Storage and load balancers need their own identity

We estimated persistent-volume cost from provisioned capacity and a per-storage-class coefficient, turning a monthly rate into an hourly one using a 30-day month. That's an explicit approximation. It doesn't cover every IOPS, throughput, snapshot, or related storage charge.

Volume ownership has to stay visible after the pod is gone. Keeping a volume can be the right recovery decision and it still needs an application or team to own the cost. Match each volume to its claim and namespace, keep the cluster in scope, and decide how orphaned or shared volumes are handled.

The ingress proxy used a fixed load-balancer coefficient. Several Ingress resources can share one physical load balancer, so counting each ingress as its own load balancer overstates the base cost. Some of the DTE and cluster dashboards tried to group them. That logic also needs a consistent scope and a defined way to split the cost between the workloads sharing it.

Traffic-based load-balancer costs and other shared costs need more work still. DNS, NAT, logging, databases, support, and data transfer don't disappear just because a pod allocation series doesn't include them.

How Grafana made the result useful

Our dashboards give concrete examples. The DTE overview grouped hourly namespace estimates by owner. Deployment and StatefulSet views showed workload estimates. An application view combined the CPU, memory, and ingress proxies. A cluster view compared workload and node estimates and broke them down by namespace.

For a team view, I'd keep owner or cost center, application, environment, and cluster as consistent filters, and show the allocation rate next to requested and used resources. Let people drill from a team total down to an application, namespace, and workload, instead of asking them to read one giant cloud-spend chart.

The most important panels sit alongside: the exceptions. Missing owners, conflicting metadata, missing price data, volumes with no current workload, shared capacity, and gaps in rule evaluation. They tell you whether a low number means low demand or incomplete attribution.

An hourly estimate is a cost rate, not a counter that only goes up. Running rate() over it won't give you a bill. A period estimate means integrating the rate over time, with known sampling and explicit handling of gaps. Missing samples should show up as incomplete coverage, not get quietly smoothed into a confident monthly charge.

Moving from showback to financial chargeback

Before using the model to move budgets, I'd agree the allocation policy with engineering and finance. Decide how to split shared platform services, idle node capacity, discounts, credits, and unallocated resources. Decide whether teams pay for reserved capacity, measured consumption, or a defined mix of the two.

Then reconcile the summed allocation against the chosen billing total for the same scope and period, and explain whatever's left over. A price estimate, a list-price view, and an amortized net billing view are different bases and can't be compared without adjusting.

To validate, test the rules with missing ownership, duplicate metadata, the same pod name in different clusters, Pending and Running phases, retained volumes, grouped ingress, and missing price series. Test the aggregation invariant: team totals plus the shared and unallocated buckets should add up to the model total. Then test the reconciliation to billing separately.

That's why I like recording rules as a foundation for FinOps. They make the definitions reusable and easy to inspect. The real value comes from keeping those definitions consistent, keeping the evidence you need to explain a number, and giving the owning team a practical next step.
